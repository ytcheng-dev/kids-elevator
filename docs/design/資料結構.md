# 資料結構

本文件分兩個區域：

- **一、欄位速查**：開發中需要立即查詢的資訊——欄位名稱、型別、初始值、數值意義。只看目前的正確狀態，不含歷史沿革。
- **二、設計考量與取捨**：需要判斷「為什麼這樣設計」或評估是否要調整某個欄位時才需要查閱。同一個決定如果經過反覆調整，只保留「最後被捨棄的做法＋捨棄原因」與「最終定案＋定案理由」，不記錄過程中每一步的時間點。

## 一、欄位速查

### Elevator（`models/elevator.dart`）

電梯本身的運行狀態。樓層數字慣例：B2 = -2 ... 1 樓 = 0 ... 5 樓 = 4。

- `currentFloor: int` — 當前樓層，初始 `0`
- `direction: Direction`（`down` / `idle` / `up`）— 行進方向，初始 `idle`
- `lastDirection: Direction`（僅會是 `up` / `down`）— 最後一次實際移動的方向，初始 `up`（首次移動前必被覆寫，初始值本身無意義）
- `doorStatus: DoorStatus`（`closed` / `closing` / `opening` / `open`）— 門狀態，初始 `closed`
- `openedAt: DateTime?` — 完成開門的時間點；關門完成時重設為 `null`
- `isStartLongPress: bool` — 是否正在長按開門鍵，初始 `false`

### FloorButton（`models/panel_buttons.dart`）

- `title: String`（final）— 樓層顯示文字
- `audioFile: String`（final）— 抵達該樓層時要播放的語音檔路徑（相對於 `assets/` 資料夾，例如 `'sounds/floor_B1.mp3'`），供 `VoicePlayer.request()` 使用
- `isTarget: bool` — 是否為目標樓層，初始 `false`，電梯抵達後自動清除
- 集合管理：`floorMap: Map<int, FloorButton>`，key 為樓層數字，存放於 `_MyHomePageState`

### ActionButton（`models/panel_buttons.dart`）

- `title: String`（final）— 按鈕文字
- `iconCode: IconData`（final）— 按鈕圖示
- `btnType: ActionType`（final，`open` / `close`）— 對應的行為
- `audioFile: String`（final）— 該動作（開門／關門）觸發時要播放的語音檔路徑，供 `VoicePlayer.request()` 使用
- 全部欄位皆為 `final`，純資料物件；按壓中的視覺回饋改由 `DoorButton` 自己的 local state 管理，詳見 `元件結構.md`
- 集合管理：`actionMap: Map<ActionType, ActionButton>`，存放於 `_MyHomePageState`

### TimerManager（`models/timer_manager.dart`）

集中管理電梯所有非同步等待/過渡時間。

秒數／毫秒常數（`static const int`）：

- `doorProcTime = 3`（秒）— 開/關門執行時間
- `floorTime = 2`（秒）— 樓層移動時間
- `openWaitingTime = 5`（秒）— 開門後預設等待關門時間
- `longPressOpenTime = 2`（秒）— 長按開門放開後，等待關門時間
- `switchTime = 500`（毫秒）— 關門完成後，轉換成移動前的緩衝時間

方法：

- `startTimer(TimerType type, VoidCallback cb)` — 依 `type` 查表決定秒數；啟動前自動 `clear()` 舊計時器
- `startSelfTimer(Duration duration, VoidCallback cb)` — 秒數為動態算出時使用（非查表）
- `clear()` — 取消目前的計時器

內部只有一個 `Timer? _pendingTimer` 欄位（同一時間只會有一個計時器在等待）。

### VoicePlayer（`models/voice_player.dart`，Phase 16 前叫 `AudioManager`／`models/audio_manager.dart`，詳見下方設計考量）

集中管理語音播報播放，內建「最多一個等待中音檔」的播放佇列，並支援播放完成後的 callback。

欄位：

- `_audioPlayer: AudioPlayer`（final）— `audioplayers` 套件的底層播放器實例
- `isPlaying: bool` — 目前是否正在播放中，初始 `false`。自行維護、在 `_play()` 內同步設定，不依賴 `_audioPlayer.state`（詳見下方設計考量）
- `_nextFile: String?` — 等待中的音檔路徑
- `_nextTask: VoidCallback?` — 等待中音檔播放完成後要執行的 callback
- `_targetTask: VoidCallback?` — 目前正在播放的音檔，播放完成後要執行的 callback

方法：

- `request({required bool isAllow, required String fileName, VoidCallback? cb})` — `isAllow` 由呼叫端傳入（Phase 16 起改由 `providers/volume.dart` 的 `volumeProvider` 管理，這個 class 本身不再持有，詳見下方設計考量與 `狀態管理結構.md`）；為 `false` 時直接呼叫 `cb?.call()`（若有提供）後即返回，不進入播放佇列；為 `true` 時，若目前沒有東西在播，立即播放；否則存入等待欄位（最多保留一個，新的請求會直接取代還沒播出來的舊請求）
- `_play()`（私有）— 把等待欄位（`_nextFile`／`_nextTask`）的內容取出、轉存到「目前正在播放」欄位（`_targetTask`），並呼叫 `_audioPlayer.play(AssetSource(...))`
- `clear()` — 清除等待中的音檔（不影響目前正在播放的）
- `dispose()` — 呼叫 `_audioPlayer.dispose()` 釋放資源，由 `_PanelPageState.dispose()` 呼叫

建構子內註冊 `_audioPlayer.onPlayerComplete` 監聽：先呼叫 `_targetTask?.call()`（剛播完那個音檔的 callback）、清空 `_targetTask`、重設 `isPlaying = false`，最後呼叫 `_play()`（若等待欄位有東西就接著播）。

### SfxPlayer（`models/sfx_player.dart`）

集中管理按鈕觸發的短促提示音效播放。與 `VoicePlayer` 各自獨立——各自持有獨立的 `AudioPlayer` 實例、獨立的播放狀態，播放策略也不同（詳見下方設計考量）。

欄位：

- `_audioPlayer: AudioPlayer`（final）— `audioplayers` 套件的底層播放器實例，建構子內設定 `AudioContextConfig(focus: AudioContextConfigFocus.mixWithOthers)`（詳見下方設計考量）
- `audioFile: String`（final）— 音效檔路徑，所有按鈕（樓層鈕、開關門鈕）共用同一個檔案，不需要依呼叫端傳入
- `isPlaying: bool` — 目前是否正在播放中，初始 `false`

方法：

- `request({required bool isAllow})` — `isAllow` 由呼叫端傳入（Phase 16 起改由 `providers/volume.dart` 的 `volumeProvider` 管理，這個 class 本身不再持有，詳見下方設計考量與 `狀態管理結構.md`）；為 `false`，或目前有音效正在播放中，直接不處理（忙碌就丟棄，不排隊）；否則立即播放
- `_play()`（私有）— 設定 `isPlaying = true`，呼叫 `_audioPlayer.play(AssetSource(audioFile))`
- `dispose()` — 呼叫 `_audioPlayer.dispose()` 釋放資源

建構子內註冊 `_audioPlayer.onPlayerComplete` 監聽：重設 `isPlaying = false`。

### PanelPageCss（`styles/css_manager.dart`）

所有成員皆為 `static`。

顏色常數：

- `backgroundGray` — 按鈕底色
- `defaultBlack` — 一般狀態的邊框/文字/圖示色（實際為灰紫色，非純黑）
- `highlight` — 選中/按壓中的強調色（樓層鈕、開關門鈕共用）
- `screenText` — 樓層顯示區域文字/圖示顏色

尺寸常數：

- `shortSidePercent = 0.35`
- `longSidePercent = 0.18`

（依版面方向決定哪個對應寬、哪個對應高，搭配 `LayoutBuilder` 讀到的可用空間，兩個方向都算一次尺寸，取較小值。）

方法：

- `buttonDecoration(bool isHighlight)` — 回傳對應的 `BoxDecoration`
- `getButtonBox(Widget btn, double width)` — 包裝 `SizedBox` + `AspectRatio(1)`，回傳正方形按鈕容器

### AnimateOffset（`models/animate_offset.dart`）

建構子：`AnimateOffset({required AnimationController animateController})`——`animateController` 只在建構當下用來算出 6 個 Animation，不保留為欄位。

大小常數（`static const double`）：

- `horizontalOffset = 0.3`
- `verticalOffset = 1`

6 個 `Animation<Offset>` 欄位（皆由 `Tween<Offset>(...).animate(animateController)` 算出）：

- `leftOpenOffset` / `rightOpenOffset` — 開門動畫，左右圖示分別向外滑開
- `leftCloseOffset` / `rightCloseOffset` — 關門動畫，左右圖示分別向內滑合
- `upFloorOffset` / `downFloorOffset` — 樓層移動方向箭頭動畫

### Enums（`models/enums.dart`）

- `Direction`：`down` / `idle` / `up`
- `DoorStatus`：`closed` / `closing` / `opening` / `open`
- `ActionType`：`open` / `close`
- `TimerType`：`doorProc` / `moveFloor` / `openWaiting` / `longPressOpen` / `doSwitch`
- `ScreenIcon`：`up` / `down` / `left` / `right`
- `VolumeType`：`sfx`（按鈕提示音效）／`voice`（語音播報）

## 二、設計考量與取捨

**`floorMap` 為什麼是 `Map<int, FloorButton>`，不是 `List` 或 `Map<String, dynamic>`**
用 `Map<String, dynamic>`（類似 JS 物件字面值）的話，巢狀值型別不一致時會被推斷成籠統的 `dynamic`，失去型別檢查與 IDE 自動完成；改用自訂 `FloorButton` class 保留明確欄位型別。用 `List<FloorButton>` 的話，index 必須從 0 開始連續，B2 對應 index 0 不直覺，日後新增樓層（如 B3）要調整既有 index；`Map<int, FloorButton>` 的 key 可以直接對應樓層數字語意（B2 = -2），新增樓層只需加一筆、不影響既有資料。`FloorButton` 原本另外設計了 `myFloor` 欄位重複記錄樓層數字，後來移除，改由 `Map` 的 key 作為樓層數字的唯一來源，避免兩處資料不同步的風險。

**`direction`／`doorStatus` 為什麼用 enum，不用整數代碼**
型別安全（編譯期避免塞入不合法值）、搭配 `switch` 有窮盡性檢查、語意比整數代碼清楚。`direction` 參與樓層移動運算時，用 if/else 或 switch 明確轉譯，不直接做算術加減，維持可讀性。

**`openedAt` 為什麼用 `DateTime?`，不是累加秒數的 `int`**
原規劃是每秒用一個 `Timer` 累加 `openTime: int`。最終改成「只記錄開門完成的時間點，需要時用 `.difference()` 現場算出已經過的時間」，理由：畫面不需要每秒顯示倒數、不用多開一個每秒觸發 `setState()` 的 `Timer`，也沒有累積誤差的風險。

**`lastDirection` 存在的理由**
電梯到達目標樓層、完成開關門後，需要決定接下來優先往哪個方向檢查是否還有其他目標樓層。此時 `direction` 已經是 `idle`，拿不到「原本往哪個方向走」的資訊，因此另外記錄最後一次實際移動的方向。

**`floorMap` 為什麼沒有放進 `Elevator` class**
`floorMap`（樓層按鈕/UI 選取狀態）跟 `Elevator`（電梯實際運行狀態）職責不同，刻意分開管理，`floorMap` 留在 `_MyHomePageState`。

**`TimerManager` 為什麼只用一個 `_pendingTimer` 欄位，不是每種計時各自一個欄位**
「樓層移動」、「開關門過渡」、「開門後等待」、「長按放開後等待」、「關門後轉換成移動前的緩衝」這幾種計時彼此互斥、不會同時發生，不需要各自獨立欄位。`startTimer()` 啟動前一定先 `clear()` 舊計時器，呼叫端不需要自己負責取消，也避免「殭屍 Timer」——例如關門中途被使用者按下開門，舊計時器卻還在跑、覆蓋掉新狀態。

**秒數常數為什麼放在 `TimerManager`，不放在 `Elevator`**
只有計時器邏輯本身需要參考這些數字，集中維護不用在兩個 class 之間對照。

**`startSelfTimer()` 為什麼跟 `startTimer()` 分開**
`startTimer()` 是查表決定秒數；長按放開後要依「已經過的開門時間」反推剩餘秒數，秒數是動態算出來的，跟查表是不同語意，獨立成另一個方法避免同一個函式簽章身兼兩種用途。

**`doSwitch` 這個 `TimerType` 為什麼存在，`switchTime` 為什麼用毫秒、不像其他常數用秒**
原本 `closeDoor()` 完成關門（`doorStatus` 變成 `closed`）後，會立即依 `lastDirection` 呼叫 `goUpFloor()`/`goDownFloor()`，檢查下一個目標樓層並開始移動。後來加上 `doSwitch` 這個中間計時器，在「關門完成」跟「真正觸發移動邏輯」之間留一段很短的緩衝時間，讓使用者如果關門後立刻反悔、想重新開門，還有機會按下開門鍵取消，不會門一關上就馬上被移動邏輯鎖住。這段緩衝只是提供一個操作視窗，性質跟 `openWaitingTime` 那種「使用者可感知的等待秒數」不同，因此刻意選擇很短的 `500` 毫秒、用 `milliseconds` 而不是 `seconds` 表示。

**`ActionButton` 的按壓回饋為什麼用 `Listener` 的 `onPointerDown`/`onPointerUp`/`onPointerCancel`，不用 `GestureDetector` 的 `onTapDown`/`onTapUp`**
長按情境下，`onTapDown`/`onTapUp` 會被手勢競技場（gesture arena）判定邏輯提早誤關，導致按壓視覺效果不正確；改用 `Listener` 的底層指標事件才能正確涵蓋長按情境。

**`actionMap`／`floorMap` 為什麼要在 `_MyHomePageState` 宣告一次、不能在 `build()` 裡臨時建立**
`FloorButton` 若直接在 `build()` 裡臨時建立，`isTarget` 這類會變動的欄位，會在下一次 `build()` 被重新建立、reset 回預設值。必須讓物件存活在 `State` 的欄位裡，才能跨越多次 `build()` 保存狀態。`ActionButton` 目前所有欄位皆為 `final`，理論上重建也不會遺失狀態，但為了跟 `floorMap` 的宣告方式一致、維持兩個 Map 管理方式相同的心智模型，仍然選擇一併宣告在 `_MyHomePageState`。

**`PanelPageCss` 為什麼集中管理顏色/樣式**
Flutter 沒有 CSS 那種「共用樣式類別」機制，用一個所有成員皆為 `static` 的 class 集中管理顏色常數跟樣式產生邏輯，不需要 `new` 出實例就能用。

**`PanelPageCss` 的按鈕尺寸常數為什麼是 `shortSidePercent`／`longSidePercent` 兩個，不是單一個寬度百分比**
早期做法只用「螢幕寬度百分比」反推按鈕高度，沒有考慮畫面垂直方向實際可用空間，某些螢幕比例下 5 顆正方形按鈕疊在一起會 overflow。改成同時準備「短邊」跟「長邊」兩個百分比常數，搭配 `LayoutBuilder` 讀取實際可用寬高約束，寬度、高度都各自反推一次尺寸、取較小值，才能真正兼顧兩個方向的可用空間。

**`AnimateOffset` 的 6 個位移量為什麼統一用同一組 `horizontalOffset`／`verticalOffset` 常數**
原始設計中，開門/關門動畫左右兩側的位移量並不對稱（例如一側 0.2、另一側 0.3）。元件化重構時決定統一成同一個數值，簡化維護，接受這個小幅視覺差異的取捨。

**`AnimateOffset` 為什麼不保留 `AnimationController` 欄位**
`SlideTransition` 之類的動畫 widget，是直接訂閱（listen）傳入的 `Animation` 物件本身的變化來局部重繪，不需要透過 Controller 或外層 `setState()` 才能動起來。顯示端只需要已經算好的 `Animation<Offset>`，不需要再摸到原始 `Controller`（Controller 的啟動/停止仍由業務邏輯方法呼叫、留在 `_MyHomePageState`），因此建構子只把 `animateController` 當一次性參數使用，不存成欄位。

**`VoicePlayer` 為什麼在 Phase 16 改名為 `AudioManager`**
Phase 16 引入 Riverpod 管理跨畫面共用的音效／語音開關狀態時，專案裡陸續確立了以「Voice」代表語音播報的命名慣例（`VolumeType.voice`、`isAllowVoice`、`toggleVoice()`、`requestVoicePlayer()`），原本的 `AudioManager` 沿用「Audio」這個字，跟其餘命名不一致，因此一併改名為 `VoicePlayer`，也讓命名方式（「做什麼事＋Player」）跟 `SfxPlayer` 更一致。

**`VoicePlayer` 為什麼放在 `models/`，而不是跟 Phase 16 新增的 `providers/` 放一起**
`VoicePlayer` 本身是一個獨立自足的 class——可以在任何情境下直接 `new` 一個出來就能用，不依賴 Riverpod 或任何框架機制，符合 `models/` 一貫的性質。真正跟 Riverpod 綁在一起的，是它現在依賴外部傳入的 `isAllow` 這個值本身，而不是 `VoicePlayer` 這個 class 自己——詳見 `狀態管理結構.md` 的說明。

**`VoicePlayer` 為什麼只支援「最多一個等待中音檔」，不是真正的 Queue**
盤點電梯目前會觸發語音的情境（到達樓層、開門、關門）之後，確認任一時刻最多只會有一個音檔需要排隊等待播放，不會同時累積兩個以上，因此不需要設計真正的多筆佇列，用一個欄位存放「下一個要播的」就足夠；新的請求進來時，直接取代還沒播出來的舊請求。

**`VoicePlayer` 為什麼自己維護 `isPlaying` 布林欄位，不直接查詢 `_audioPlayer.state`**
一開始的版本是用 `_audioPlayer.state != PlayerState.playing` 判斷目前是不是有東西在播。但實測後發現 `audioplayers` 的 `.play()` 呼叫後，`.state` 不會立即同步更新成 `playing`（需要等套件內部跟原生層溝通完成才會反映），如果程式碼連續同步呼叫兩次 `request()`（例如 `moveFloor` 到達樓層時，緊接著請求 `ding` 音效跟樓層語音），第二次呼叫檢查 `.state` 時可能讀到還沒更新的舊值，誤判成「沒有東西在播」而立刻播放，蓋掉第一個其實才剛開始播、還沒真的播出來的音檔。改成自己在 `_play()` 內同步設定 `isPlaying = true`，不受套件內部非同步更新時機影響，才解決了這個 race condition。

**`onPlayerComplete` 監聽器裡，為什麼要先呼叫 `_targetTask?.call()` 再呼叫 `_play()`**
`_targetTask` 代表「目前正在播放的音檔，播完後要執行的 callback」；`_play()` 執行時會把 `_targetTask` 換成「下一個要播放的音檔」的 callback。如果順序寫反（先 `_play()` 再呼叫 `_targetTask?.call()`），呼叫到的會是新換上去的下一個 callback，而不是真正剛播完那個音檔對應的 callback，導致 callback 被錯誤觸發、原本該被呼叫的那個反而遺失。必須先讀取／呼叫舊值，再讓 `_play()` 覆寫。

**`VoicePlayer` 為什麼不需要在 `.play()` 前呼叫 `.stop()`**
`audioplayers` 的 `.play()` 本身會自動處理「切換播放來源」，不像 `AnimationController.forward()` 那樣需要手動 `stop()`/`reset()` 才能重新開始。而且 `VoicePlayer` 的整體設計已經確保 `_play()` 只會在「目前沒有東西在播放」（`isPlaying == false`）時才被呼叫，不會出現「在播放中又呼叫 `.play()`」的情境，因此不需要額外呼叫 `.stop()`。

**`AssetSource` 的路徑為什麼不能包含 `assets/` 前綴**
`audioplayers` 的 `AssetSource` 是套件自己設計的 API，內部會自動幫路徑補上 `assets/` 前綴，跟 Flutter 框架本身 `Image.asset()`／`AssetImage`「路徑要完全對應 `pubspec.yaml` 宣告」的慣例不同。如果呼叫端自己也寫了 `assets/`，會變成重複前綴（`assets/assets/...`），導致找不到檔案。因此 `FloorButton.audioFile`／`ActionButton.audioFile`／`SfxPlayer.audioFile` 存放的路徑一律不含 `assets/` 前綴（例如 `'sounds/floor_B1.mp3'`、`'sounds/button.mp3'`）。

**`clear()` 目前只清除 `_nextFile`，沒有一併清除 `_nextTask`／`_targetTask`**
討論當下曾經設想「電梯已經開始移動、需要取消還沒播出來的關門語音」的情境，但實際檢視業務邏輯後發現：關門語音播放完成的時間點，一定早於下一次語音事件（下一次抵達樓層、或需要等關門完全結束才能再次開門），佇列機制本身已經天然避免了這個衝突，目前不需要真的呼叫 `clear()`。`clear()` 保留作為防禦性設計，之後如果業務邏輯有變動、真的需要中途取消時可以直接使用。

**`VoicePlayer.request()` 為什麼在 `isAllow` 為 `false` 時仍要呼叫 `cb?.call()`，不是直接不處理**
`cb` 不只是「音檔播完的通知」，也承載了業務邏輯——例如樓層抵達語音的 callback 裡會執行 `setElevatorDirection(Direction.idle)`、清除 `isTarget`、呼叫 `openDoor()`。如果關閉語音時直接略過 callback，會連帶讓這些業務邏輯永遠不會執行，電梯狀態機會卡住（例如永遠停在移動中、不會開門）。因此 `isAllow`（Phase 16 起改由呼叫端傳入）只決定「聲音要不要真的播出來」，完全不影響 callback 是否執行，兩者刻意分開判斷。

**`SfxPlayer` 為什麼獨立設計一個新 class，不重用 `VoicePlayer`**
`VoicePlayer` 的排隊機制（忙碌時把新請求存進等待欄位，前一個播完接著播）是為語音播報「循序播報、不能被打斷」的情境設計的；按鈕音效需要的行為是「忙碌就直接丟棄，不用排隊」，兩者播放策略本質不同。此外，按鈕音效跟語音播報需要各自獨立的「播放中」狀態——語音播放中按鈕音效仍要能正常響，反之亦然——代表兩者需要各自獨立的 `AudioPlayer` 實例，不能共用同一個忙碌旗標。基於以上兩點，設計上讓 `SfxPlayer` 完全獨立，不重用 `VoicePlayer` 的任何邏輯。

**`SfxPlayer` 為什麼要設定 `AudioContextConfig(focus: AudioContextConfigFocus.mixWithOthers)`**
`AudioPlayer` 播放時預設會嘗試取得系統音訊焦點（Android/iOS 用來協調「同一時間誰可以播放聲音」的機制）；`SfxPlayer`、`VoicePlayer` 兩個播放器實例同時存在時，若都用預設設定各自搶焦點，會導致其中一個播放中途被系統中斷、`onPlayerComplete` 沒有正常觸發（進而連帶影響依賴該 callback 的業務邏輯）。改用 `mixWithOthers` 讓 `SfxPlayer` 不參與焦點協調，允許跟其他播放器混音播放，避免互相干擾。曾評估改用 `PlayerMode.lowLatency`（Android 底層改用 `SoundPool`）同時解決焦點與播放延遲的問題，但套件文件明確指出 `lowLatency` 模式下 `onPlayerComplete` 不會觸發，與 `SfxPlayer`「忙碌就丟棄」機制所需要的完成通知互相衝突，因此改回預設的 `PlayerMode.mediaPlayer`，只透過 `AudioContext` 調整焦點行為，不改變播放模式。

**`SfxPlayer`／`VoicePlayer` 的 `isAllow` 為什麼從物件內部欄位，改成 Phase 16 由 `request()` 參數傳入**
Phase 15 以前，`isAllow` 各自放在 `SfxPlayer`／`AudioManager`（現 `VoicePlayer`）物件內部，理由是這兩個物件本身就是 `_PanelPageState` 的欄位，比照 `elevator.direction` 等既有欄位的做法，UI 直接讀寫這些物件內部的屬性、包在 `setState()` 觸發重繪即可，不需要在 `_MyHomePageState`／`_PanelPageState` 額外維護一份重複鏡射的 `bool`。Phase 16 引入 Riverpod、讓 `isAllow` 變成跨畫面（`HomePage`／`PanelPage`）共用的狀態後，這個前提不再成立——`HomePage` 也需要讀寫同一份 `isAllow`，不能再只放在只活在 `PanelPage` 生命週期裡的物件內部。最終決定把 `isAllow` 整個搬到 `providers/volume.dart` 的 `volumeProvider`，`SfxPlayer`／`VoicePlayer` 內部完全拿掉這個欄位，改成 `request()` 方法多接受一個 `required bool isAllow` 參數，判斷邏輯（能不能播放、callback 是否照樣執行）維持不變、只是搬進方法內部；這樣做也刻意避免讓這兩個 class 直接依賴 `WidgetRef`／Riverpod，維持 `models/` 的框架無關性（詳見 `狀態管理結構.md`）。
