# 資料結構
1. 電梯記錄（`Elevator` class）
    + currentFloor: 當前樓層。與 2. 的 `floorMap` key 使用同一套樓層數字（B2 = -2 ... 5樓 = 4），初始為 0（對應 1 樓）
    + direction: 行進方向。實作為 `enum Direction { down, idle, up }`（對應原始定義 -1 = 下樓, 0 = 停止, 1 = 上樓），初始為 `idle`
    + lastDirection: 最後一次實際移動的方向（`Direction`，不含 `idle`）。用途：電梯停下、開關門完成後，優先延續同一方向檢查是否還有其他目標樓層，初始為 `up`（實際使用前一定會被第一次移動覆寫）
    + doorStatus: 門狀態。實作為 `enum DoorStatus { closed, closing, opening, open }`（對應原始定義 0 = 已關門, 1 = 關門中, 9 = 開門中, 10 = 已開門），初始為 `closed`
    + openedAt: 門開啟完成的時間點，型別為 `DateTime?`，關門完成時重設為 `null`。Phase 5 最終決定改用「記錄時間點、需要時用 `.difference()` 現場算已開門時間」的設計，取代原本規劃的「每秒累加秒數」（`openTime: int`）寫法，理由：沒有畫面需要每秒顯示倒數，避免多開一個每秒觸發 `setState()` 的 `Timer`，也不會有累積誤差（詳見 `Phase5_學習紀錄.md` 第二節之7）
    + isStartLongPress: 是否正在長按開門按鈕（`bool`），用於讓非同步的開門完成流程可以在自己觸發的當下查詢「使用者現在是否還按著」，藉此決定是否要照正常的 5 秒倒數自動關門（詳見 `Phase5_學習紀錄.md` 第二節之8）
    + countForClose: 原始設計用途為「讀秒確認執行關門」，Phase 5 實作後改用 `openedAt` 時間戳記涵蓋了原本要交給它的用途，目前宣告但**尚未實際使用**，待 Phase 6 開始前確認是否移除
2. 樓層按鈕與樓層集合
    + floorMap: 所有樓層電梯按鈕的集合，實作上使用 `Map<int, FloorButton>`，key 為樓層數字（B2 = -2 ... 5樓 = 4），value 為下方樓層按鈕。依序涵蓋 B2, B1, 1, 2, 3, 4, 5（對應 key: -2, -1, 0, 1, 2, 3, 4）。與「電梯記錄」的 `Elevator` class 分開管理（職責不同：樓層按鈕/UI 狀態 vs. 電梯運行狀態），存放於 `_MyHomePageState`
    + isTarget: 是否被標記為目標樓層（`FloorButton` 的欄位）。電梯抵達該樓層時會自動清為 `false`
3. 開門/關門按鈕（`ActionButton` class）
    + title: 按鈕顯示文字
    + btnType: 代表的行為。實作為 `enum ActionType { open, close }`（對應原始定義 1 = 開門, 2 = 關門）
    + `ActionButton` 所有欄位皆為 `final`（不像 `FloorButton` 需要記住會變動的 `isTarget`，這個按鈕本身沒有需要保存的狀態）
4. 計時器管理（`TimerManager` class）
    + 集中管理電梯運作過程中所有非同步的等待/過渡時間，透過 `enum TimerType { doorProc, moveFloor, openWaiting, longPressOpen }` 標示目前在等待的是哪一種行為
    + 內部只用一個 `Timer? _pendingTimer` 欄位追蹤目前（唯一）可能存在的計時器——因為「移動」、「開關門過渡」、「開門後等待」、「長按放開後等待」彼此互斥，不會同時發生，不需要各自獨立欄位
    + `startTimer(type, callback)`: 啟動前一定先呼叫 `clear()` 取消前一個尚未觸發的計時器，讓呼叫端不需要自己負責「取消舊計時器」，避免殭屍 Timer（例如關門中被使用者中途按下開門）
    + `startSelfTimer(duration, callback)`: 用於秒數是動態算出來（例如長按放開後，依「已開門時間」反推剩餘等待秒數），不查表的情境；與 `startTimer()` 分開，避免同一個函式簽章身兼兩種語意
    + `doorProcTime`（1秒）、`floorTime`（2秒）、`openWaitingTime`（5秒）、`longPressOpenTime`（2秒）四個秒數常數（`static const`）放在這裡而非 `Elevator`：因為只有計時器邏輯本身需要參考這些數字，集中維護不用在兩個 class 之間對照
    + 實例存放於 `_MyHomePageState`（跟 `elevator`、`floorMap` 平行）
---
 
## 異動紀錄
- Phase 5 對話開始時同步：將原本「1. 電梯記錄」中的 `floorList`（陣列）改為 `floorMap`（`Map<int, FloorButton>`），並移除「2. 樓層按鈕」中的 `myFloor` 欄位，反映 Phase 4 的實作決策（詳見 `Phase4_學習紀錄.md` 第六節「資料結構設計決策」）。
- Phase 5：「電梯記錄」實際實作為獨立的 `Elevator` class（`currentFloor`/`direction`/`doorStatus`/`openTime`/`countForClose`）。`direction`、`doorStatus` 決定改用 Dart `enum`（而非純數字）表達，理由：型別安全（編譯期避免塞入不合法值）、搭配 `switch` 有窮盡性檢查、語意更清楚；`direction` 參與樓層移動運算時改用 if/else 或 switch 明確轉譯，不直接做算術加減，以維持可讀性。原本歸在「電梯記錄」底下的 `floorMap`，因與電梯運行狀態職責不同，拆分為獨立的「樓層按鈕與樓層集合」項目，實作上維持在 `_MyHomePageState`、不放進 `Elevator` class。`openTime`/`countForClose` 的確切型別與用法（是否維持累加秒數的 `int`，或改為時間戳記式設計）留待「長按延長開門時間」階段一併確認。
- Phase 5：新增 `lastDirection`（記住最後一次實際移動方向），用於電梯關門完成後決定優先檢查哪個方向是否還有其他目標樓層，避免遺失「原本往哪個方向走」的資訊。
- Phase 5：新增「開門/關門按鈕」的 `ActionButton` class（`title`/`btnType`），取代原本只傳文字的做法，讓按鈕點擊能正確分派到 `openDoor()`/`closeDoor()`。
- Phase 5：新增 `TimerManager` class 與 `TimerType` enum，集中管理電梯所有非同步計時（樓層移動、開關門過渡、開門後等待）。原本規劃放在 `Elevator` 的 `floorTime`/`doorProcTime`/`openWaitingTime` 三個秒數常數，改放到 `TimerManager`，因為只有計時器邏輯本身需要參考它們，避免維護時要在兩個 class 之間對照。這個設計也一併解決了「關門中被使用者按下開門」時，舊計時器沒有被取消、可能覆蓋新狀態的「殭屍 Timer」問題（對應需求 9）。
- Phase 5 收尾：「長按延長開門時間」階段確認 `openTime` 最終改名為 `openedAt`、型別定為 `DateTime?`（記錄時間點，而非累加秒數的 `int`），並新增 `isStartLongPress`（`bool`）欄位、`TimerType.longPressOpen` 與對應的 `TimerManager.longPressOpenTime`（2秒）常數、`TimerManager.startSelfTimer()`。`countForClose` 欄位在 Phase 5 中始終未被實際使用，標記為待 Phase 6 開始前確認是否移除。
