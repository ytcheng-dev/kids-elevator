# 資料結構

本文件分兩個區域：

- **一、欄位速查**：開發中需要立即查詢的資訊——欄位名稱、型別、初始值、數值意義。只看目前的正確狀態，不含歷史沿革。
- **二、設計考量與取捨**：需要判斷「為什麼這樣設計」或評估是否要調整某個欄位時才需要查閱。同一個決定如果經過反覆調整，只保留「最後被捨棄的做法＋捨棄原因」與「最終定案＋定案理由」，不記錄過程中每一步的時間點。

---

## 一、欄位速查

### Elevator（`models/elevator.dart`）

電梯本身的運行狀態。樓層數字慣例：B2 = -2 ... 1 樓 = 0 ... 5 樓 = 4。

- `currentFloor: int` — 當前樓層，初始 `0`
- `direction: Direction`（`down` / `idle` / `up`）— 行進方向，初始 `idle`
- `lastDirection: Direction`（僅會是 `up` / `down`）— 最後一次實際移動的方向，初始 `up`（首次移動前必被覆寫，初始值本身無意義）
- `doorStatus: DoorStatus`（`closed` / `closing` / `opening` / `open`）— 門狀態，初始 `closed`
- `openedAt: DateTime?` — 完成開門的時間點；關門完成時重設為 `null`
- `isStartLongPress: bool` — 是否正在長按開門鍵，初始 `false`

### FloorButton（`models/board_button.dart`）

- `title: String`（final）— 樓層顯示文字
- `isTarget: bool` — 是否為目標樓層，初始 `false`，電梯抵達後自動清除
- 集合管理：`floorMap: Map<int, FloorButton>`，key 為樓層數字，存放於 `_MyHomePageState`

### ActionButton（`models/board_button.dart`）

- `title: String`（final）— 按鈕文字
- `iconCode: IconData`（final）— 按鈕圖示
- `btnType: ActionType`（final，`open` / `close`）— 對應的行為
- `isPressed: bool`（可變）— 按壓中的視覺回饋，初始 `false`
- 集合管理：`actionMap: Map<ActionType, ActionButton>`，存放於 `_MyHomePageState`

### TimerManager（`models/timer_manager.dart`）

集中管理電梯所有非同步等待/過渡時間。

秒數常數（`static const int`）：

- `doorProcTime = 3` — 開/關門執行時間
- `floorTime = 2` — 樓層移動時間
- `openWaitingTime = 5` — 開門後預設等待關門時間
- `longPressOpenTime = 2` — 長按開門放開後，等待關門時間

方法：

- `startTimer(TimerType type, VoidCallback cb)` — 依 `type` 查表決定秒數；啟動前自動 `clear()` 舊計時器
- `startSelfTimer(Duration duration, VoidCallback cb)` — 秒數為動態算出時使用（非查表）
- `clear()` — 取消目前的計時器

內部只有一個 `Timer? _pendingTimer` 欄位（同一時間只會有一個計時器在等待）。

### CSSManager（`styles/css_manager.dart`）

所有成員皆為 `static`。

顏色常數：

- `backgroundGray` — 按鈕底色
- `defaultBlack` — 一般狀態的邊框/文字/圖示色（實際為灰紫色，非純黑）
- `highlight` — 選中/按壓中的強調色（樓層鈕、開關門鈕共用）
- `screenText` — 樓層顯示區域文字/圖示顏色

尺寸常數：

- `shortSidePercent = 0.35`
- `longSidePercent = 0.18`

（依版面方向決定哪個對應寬、哪個對應高，搭配 `LayoutBuilder` 讀到的可用空間，兩個方向都算一次尺寸，取較小值。）

方法：

- `buttonDecoration(bool isHighlight)` — 回傳對應的 `BoxDecoration`
- `getButtonBox(Widget btn, double width)` — 包裝 `SizedBox` + `AspectRatio(1)`，回傳正方形按鈕容器

### AnimateOffset（`models/animate_offset.dart`）

建構子：`AnimateOffset({required AnimationController animateController})`——`animateController` 只在建構當下用來算出 6 個 Animation，不保留為欄位。

大小常數（`static const double`）：

- `horizontalOffset = 0.3`
- `verticalOffset = 1`

6 個 `Animation<Offset>` 欄位（皆由 `Tween<Offset>(...).animate(animateController)` 算出）：

- `leftOpenOffset` / `rightOpenOffset` — 開門動畫，左右圖示分別向外滑開
- `leftCloseOffset` / `rightCloseOffset` — 關門動畫，左右圖示分別向內滑合
- `upFloorOffset` / `downFloorOffset` — 樓層移動方向箭頭動畫

### Enums（`models/enums.dart`）

- `Direction`：`down` / `idle` / `up`
- `DoorStatus`：`closed` / `closing` / `opening` / `open`
- `ActionType`：`open` / `close`
- `TimerType`：`doorProc` / `moveFloor` / `openWaiting` / `longPressOpen`
- `ScreenIcon`：`up` / `down` / `left` / `right`

## 二、設計考量與取捨

**`floorMap` 為什麼是 `Map<int, FloorButton>`，不是 `List` 或 `Map<String, dynamic>`**
用 `Map<String, dynamic>`（類似 JS 物件字面值）的話，巢狀值型別不一致時會被推斷成籠統的 `dynamic`，失去型別檢查與 IDE 自動完成；改用自訂 `FloorButton` class 保留明確欄位型別。用 `List<FloorButton>` 的話，index 必須從 0 開始連續，B2 對應 index 0 不直覺，日後新增樓層（如 B3）要調整既有 index；`Map<int, FloorButton>` 的 key 可以直接對應樓層數字語意（B2 = -2），新增樓層只需加一筆、不影響既有資料。`FloorButton` 原本另外設計了 `myFloor` 欄位重複記錄樓層數字，後來移除，改由 `Map` 的 key 作為樓層數字的唯一來源，避免兩處資料不同步的風險。

**`direction`／`doorStatus` 為什麼用 enum，不用整數代碼**
型別安全（編譯期避免塞入不合法值）、搭配 `switch` 有窮盡性檢查、語意比整數代碼清楚。`direction` 參與樓層移動運算時，用 if/else 或 switch 明確轉譯，不直接做算術加減，維持可讀性。

**`openedAt` 為什麼用 `DateTime?`，不是累加秒數的 `int`**
原規劃是每秒用一個 `Timer` 累加 `openTime: int`。最終改成「只記錄開門完成的時間點，需要時用 `.difference()` 現場算出已經過的時間」，理由：畫面不需要每秒顯示倒數、不用多開一個每秒觸發 `setState()` 的 `Timer`，也沒有累積誤差的風險。

**`lastDirection` 存在的理由**
電梯到達目標樓層、完成開關門後，需要決定接下來優先往哪個方向檢查是否還有其他目標樓層。此時 `direction` 已經是 `idle`，拿不到「原本往哪個方向走」的資訊，因此另外記錄最後一次實際移動的方向。

**`floorMap` 為什麼沒有放進 `Elevator` class**
`floorMap`（樓層按鈕/UI 選取狀態）跟 `Elevator`（電梯實際運行狀態）職責不同，刻意分開管理，`floorMap` 留在 `_MyHomePageState`。

**`TimerManager` 為什麼只用一個 `_pendingTimer` 欄位，不是每種計時各自一個欄位**
「樓層移動」、「開關門過渡」、「開門後等待」、「長按放開後等待」四種計時彼此互斥、不會同時發生，不需要各自獨立欄位。`startTimer()` 啟動前一定先 `clear()` 舊計時器，呼叫端不需要自己負責取消，也避免「殭屍 Timer」——例如關門中途被使用者按下開門，舊計時器卻還在跑、覆蓋掉新狀態。

**秒數常數為什麼放在 `TimerManager`，不放在 `Elevator`**
只有計時器邏輯本身需要參考這些數字，集中維護不用在兩個 class 之間對照。

**`startSelfTimer()` 為什麼跟 `startTimer()` 分開**
`startTimer()` 是查表決定秒數；長按放開後要依「已經過的開門時間」反推剩餘秒數，秒數是動態算出來的，跟查表是不同語意，獨立成另一個方法避免同一個函式簽章身兼兩種用途。

**`ActionButton` 的按壓回饋為什麼用 `Listener` 的 `onPointerDown`/`onPointerUp`/`onPointerCancel`，不用 `GestureDetector` 的 `onTapDown`/`onTapUp`**
長按情境下，`onTapDown`/`onTapUp` 會被手勢競技場（gesture arena）判定邏輯提早誤關，導致按壓視覺效果不正確；改用 `Listener` 的底層指標事件才能正確涵蓋長按情境。

**`actionMap`／`floorMap` 為什麼要在 `_MyHomePageState` 宣告一次、不能在 `build()` 裡臨時建立**
`ActionButton`/`FloorButton` 若直接在 `build()` 裡臨時建立，`isPressed`/`isTarget` 這類會變動的欄位，會在下一次 `build()` 被重新建立、reset 回預設值。必須讓物件存活在 `State` 的欄位裡，才能跨越多次 `build()` 保存狀態。

**`CSSManager` 為什麼集中管理顏色/樣式**
Flutter 沒有 CSS 那種「共用樣式類別」機制，用一個所有成員皆為 `static` 的 class 集中管理顏色常數跟樣式產生邏輯，不需要 `new` 出實例就能用。

**`CSSManager` 的按鈕尺寸常數為什麼是 `shortSidePercent`／`longSidePercent` 兩個，不是單一個寬度百分比**
早期做法只用「螢幕寬度百分比」反推按鈕高度，沒有考慮畫面垂直方向實際可用空間，某些螢幕比例下 5 顆正方形按鈕疊在一起會 overflow。改成同時準備「短邊」跟「長邊」兩個百分比常數，搭配 `LayoutBuilder` 讀取實際可用寬高約束，寬度、高度都各自反推一次尺寸、取較小值，才能真正兼顧兩個方向的可用空間。

**`AnimateOffset` 的 6 個位移量為什麼統一用同一組 `horizontalOffset`／`verticalOffset` 常數**
原始設計中，開門/關門動畫左右兩側的位移量並不對稱（例如一側 0.2、另一側 0.3）。元件化重構時決定統一成同一個數值，簡化維護，接受這個小幅視覺差異的取捨。

**`AnimateOffset` 為什麼不保留 `AnimationController` 欄位**
`SlideTransition` 之類的動畫 widget，是直接訂閱（listen）傳入的 `Animation` 物件本身的變化來局部重繪，不需要透過 Controller 或外層 `setState()` 才能動起來。顯示端只需要已經算好的 `Animation<Offset>`，不需要再摸到原始 `Controller`（Controller 的啟動/停止仍由業務邏輯方法呼叫、留在 `_MyHomePageState`），因此建構子只把 `animateController` 當一次性參數使用，不存成欄位。
