# 資料結構
1. 電梯記錄（`Elevator` class）
    + currentFloor: 當前樓層。與 2. 的 `floorMap` key 使用同一套樓層數字（B2 = -2 ... 5樓 = 4），初始為 0（對應 1 樓）
    + direction: 行進方向。實作為 `enum Direction { down, idle, up }`（對應原始定義 -1 = 下樓, 0 = 停止, 1 = 上樓），初始為 `idle`
    + lastDirection: 最後一次實際移動的方向（`Direction`，不含 `idle`）。用途：電梯停下、開關門完成後，優先延續同一方向檢查是否還有其他目標樓層，初始為 `up`（實際使用前一定會被第一次移動覆寫）
    + doorStatus: 門狀態。實作為 `enum DoorStatus { closed, closing, opening, open }`（對應原始定義 0 = 已關門, 1 = 關門中, 9 = 開門中, 10 = 已開門），初始為 `closed`
    + openTime: 已開門的秒數。初始為 0（目前先維持 `int`，確切型別與用法待「長按延長開門時間」階段一併確認，可能改為時間戳記式設計）
    + countForClose: 讀秒確認執行關門。初始為 0，應只有在使用者強制開門超過 5 秒後被參考/使用（型別與確切用法同上，待後續確認）
    + floorTime（`static const`）: 樓層移動時間，2 秒（對應設計主軸需求 11）
    + doorProcTime（`static const`）: 開/關門過渡狀態（`opening`/`closing`）本身的執行時間，1 秒（設計主軸未明訂此數字，Phase 5 對話中決定）
    + openWaitingTime（`static const`）: 開門完成後、無操作時的等待時間，5 秒（對應設計主軸需求 6）
2. 樓層按鈕與樓層集合
    + floorMap: 所有樓層電梯按鈕的集合，實作上使用 `Map<int, FloorButton>`，key 為樓層數字（B2 = -2 ... 5樓 = 4），value 為下方樓層按鈕。依序涵蓋 B2, B1, 1, 2, 3, 4, 5（對應 key: -2, -1, 0, 1, 2, 3, 4）。與「電梯記錄」的 `Elevator` class 分開管理（職責不同：樓層按鈕/UI 狀態 vs. 電梯運行狀態），存放於 `_MyHomePageState`
    + isTarget: 是否被標記為目標樓層（`FloorButton` 的欄位）。電梯抵達該樓層時會自動清為 `false`
3. 開門/關門按鈕
    + myAction: 代表的行為。 1 = 開門, 2 = 關門

## 異動紀錄
- Phase 5 對話開始時同步：將原本「1. 電梯記錄」中的 `floorList`（陣列）改為 `floorMap`（`Map<int, FloorButton>`），並移除「2. 樓層按鈕」中的 `myFloor` 欄位，反映 Phase 4 的實作決策（詳見 `Phase4_學習紀錄.md` 第六節「資料結構設計決策」）。
- Phase 5：「電梯記錄」實際實作為獨立的 `Elevator` class（`currentFloor`/`direction`/`doorStatus`/`openTime`/`countForClose`）。`direction`、`doorStatus` 決定改用 Dart `enum`（而非純數字）表達，理由：型別安全（編譯期避免塞入不合法值）、搭配 `switch` 有窮盡性檢查、語意更清楚；`direction` 參與樓層移動運算時改用 if/else 或 switch 明確轉譯，不直接做算術加減，以維持可讀性。原本歸在「電梯記錄」底下的 `floorMap`，因與電梯運行狀態職責不同，拆分為獨立的「樓層按鈕與樓層集合」項目，實作上維持在 `_MyHomePageState`、不放進 `Elevator` class。`openTime`/`countForClose` 的確切型別與用法（是否維持累加秒數的 `int`，或改為時間戳記式設計）留待「長按延長開門時間」階段一併確認。
- Phase 5：新增 `Elevator.floorTime`（樓層移動秒數）、`Elevator.doorProcTime`（開/關門過渡狀態執行秒數）兩個 `static const` 常數，取代原本寫死在 `Timer` 裡的數字。`floorTime` 對應設計主軸需求 11 的 2 秒；`doorProcTime`（1 秒）是 Phase 5 對話中自行決定的數字，因為設計主軸沒有明訂「開/關門動作本身」要花多久（跟「已開門要停留 5 秒」是不同的東西）。
- Phase 5：新增 `Elevator.openWaitingTime`（開門完成後無操作的等待秒數，對應需求 6 的 5 秒）與 `Elevator.lastDirection`（記住最後一次實際移動方向），用於電梯關門完成後決定優先檢查哪個方向是否還有其他目標樓層，避免遺失「原本往哪個方向走」的資訊。
