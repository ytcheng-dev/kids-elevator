# 測試結構

本文件涵蓋 `test/` 這一層——測試檔案的組織方式、測試用的替身（`fakes/`）與原生端模擬（`mocks/`），與 `資料結構.md`、`元件結構.md`、`畫面結構.md`、`狀態管理結構.md` 互補。格式比照其餘文件，分三個區域：

- **一、測試速查**：開發中需要立即查詢的資訊——目錄結構、替身與模擬的用法、共用的測試寫法。只看目前的正確狀態。
- **二、設計考量與取捨**：需要判斷「為什麼這樣設計」或評估要用哪一種替換方式時才需要查閱。
- **三、撰寫測試的注意事項**：新增或修改測試時要遵守的原則。

還沒有被測試覆蓋的程式碼與測試改善項目，記在 `測試待辦清單.md`。

## 一、測試速查

### 目錄結構

`test/` 底下的測試檔案，路徑與 `lib/` 一一對應（`lib/models/timer_manager.dart` → `test/models/timer_manager_test.dart`），另外有兩個不對應 `lib/` 的資料夾：`fakes/`、`mocks/`。

├── screens/

### `fakes/`：依賴注入用的替身

透過建構子參數或 `ProviderScope.overrides` 換掉 app 裡的真實物件，被測對象不會執行到真正的實作。

**FakeSfxPlayer**（`fakes/fake_sfx_player.dart`，`implements SfxPlayerBase`）
- `request({required bool isAllow})`：`isAllow` 為 `true` 時把 `isPlaying` 設為 `true`
- `dispose()`：把 `isDispose` 設為 `true`
- 公開欄位 `isPlaying`、`isDispose` 讓測試事後驗證；不模擬真實版本「播放中就丟棄」的行為
- 使用方式：`PanelPage(sfxPlayer: FakeSfxPlayer())`

**FakeVoicePlayer**（`fakes/fake_voice_player.dart`，`implements VoicePlayerBase`）
- 建構子：`FakeVoicePlayer({required int delaySeconds})`，用來模擬一段語音的播放長度
- `request({required bool isAllow, required String fileName, void Function()? cb})`：`isAllow` 為 `false` 時同步呼叫 `cb` 後返回（與真實版本相同）；否則排進佇列，沒有在播放時立刻開始
- 播放用一個真正的 `Timer(Duration(seconds: delaySeconds), ...)` 模擬，時間到呼叫 `cb`、接著播下一個；在 `testWidgets` 裡用 `tester.pump(Duration)` 推進
- 用 `waitForPlay` 計數器記錄排隊數量（真實版本最多只保留一個等待中的請求）
- `dispose()`：把 `isDispose` 設為 `true`，並取消還沒到期的計時器
- 公開欄位 `isPlaying`、`isDispose`、`waitForPlay` 讓測試事後驗證
- 使用方式：`PanelPage(voicePlayer: FakeVoicePlayer(delaySeconds: 1))`

**FakeVolumeNotifier**（`fakes/fake_volume_notifier.dart`，`extends VolumeNotifier`）
- 建構子：`FakeVolumeNotifier({bool isAllowSfx = false, bool isAllowVoice = false})`
- 只覆寫 `build()` 回傳指定的初始狀態；`toggleSfx()`／`toggleVoice()` 沿用真正的實作
- 使用方式：`ProviderScope(overrides: [volumeProvider.overrideWith(() => FakeVolumeNotifier(...))], child: ...)`（詳見 `狀態管理結構.md`）

### `mocks/`：模擬原生端

**MockAudioPlayersPlatform**（`mocks/mock_audioplayers_platform.dart`）

在 platform channel 上攔截 `audioplayers` 與 `path_provider` 送往原生端的訊息，讓真正的 `SfxPlayer`（以及它內部的 `AudioPlayer`）可以在 `flutter test` 裡執行。

攔截的 channel（`static const`）：

| channel | 種類 | 用途 |
|---|---|---|
| `xyz.luan/audioplayers.global` | MethodChannel | audioplayers 全域初始化（`init`） |
| `xyz.luan/audioplayers` | MethodChannel | 每個 player 的操作（`create`、`setAudioContext`、`setSourceUrl`、`resume`…），靠參數裡的 `playerId` 分辨 |
| `xyz.luan/audioplayers/events/$playerId` | EventChannel | 原生端推送事件（prepared、complete）；收到 `create` 時才知道 `playerId`，當下註冊 |
| `plugins.flutter.io/path_provider` | MethodChannel | `getTemporaryDirectory`：回傳測試用的暫存資料夾（`AssetSource` 會把 asset 寫成暫存檔） |

方法與欄位：

- `init()`：建立暫存資料夾、註冊所有 handler（`setUp` 呼叫）
- `dispose()`：取消所有 handler、刪除暫存資料夾（`tearDown` 呼叫）
- `globalMethodList`／`perMethodList`：依序記錄收到的 `MethodCall`
- `findTargetMethod(String methodName)`：從 `perMethodList` 找出第一個指定名稱的呼叫（找不到會拋 `StateError`，先用 `getMethodStrings()` 確認存在）
- `getMethodStrings()`：`perMethodList` 的 method 名稱清單
- `waitForSetAudioContext()`／`waitForResume()`：等到收到對應的呼叫為止（上限 3 秒），取代固定等待
- `pushPrepared()`／`pushComplete()`：從「原生端」推送 prepared／complete 事件；收到 `setSourceUrl` 時會自動推送 prepared

使用方式：

```dart
late MockAudioPlayersPlatform mockPlatform;

setUp(() async {
  mockPlatform = MockAudioPlayersPlatform();   // 每個測試建立新的物件
  await mockPlatform.init();
});

tearDown(() async {
  await mockPlatform.dispose();
});
```

### 各測試檔的時間控制方式

| 測試 | 時間怎麼推進 |
|---|---|
| `timer_manager_test.dart` | `fakeAsync((async) { ... async.elapse(...) })`，測試本體寫成同步函式，不用 `await` 等時間 |
| widget 測試（`screens/`、`widgets/`） | `testWidgets` 本身就在假時鐘裡執行，用 `await tester.pump(Duration)` 推進時間並畫 frame |
| `sfx_player_test.dart` | 真實時間：等 `MockAudioPlayersPlatform` 的訊號（`waitForResume()` 等）；驗證「沒發生」的情境仍用固定等待 |

### 共用的測試寫法

- **`_pumpXxx(tester, ...)`**：每個 widget 測試檔都有一個 helper，把被測元件包進 `MaterialApp`（需要時再包 `ProviderScope`）後 `pumpWidget`，例如 `_pumpFloorTile`、`_pumpDoorButton`、`_pumpPanelPage`
- **`_setPortraitScreen(tester)`**：用 `tester.view.physicalSize`（400×800）把測試畫面設成直式，並用 `addTearDown(tester.view.reset)` 在測試結束後還原（`home_page_test.dart`、`panel_page_test.dart`）
- **`diffDuration`／`_diffDuration`（1 毫秒）**：計時相關測試的邊界檢查單位——差 1 毫秒還沒觸發、補 1 毫秒已觸發（`timer_manager_test.dart` 為 `diffDuration`，`panel_page_test.dart` 為 `_diffDuration`）
- **key**：`floorTile${Floor.title}`（樓層按鈕）、`volumeRow`／`volumeSFX`／`volumeVoice`（主選單開關）、`border-container`／`icon-container`（`QuestionButton`），詳見 `畫面結構.md`、`元件結構.md`
- **`panel_page_test.dart` 的流程 helper**：`_checkMoveSingle`（移動一層並停靠的完整流程）、`_checkGoThroughFloor`（逐層經過）、`_checkFloorTileDecoration`（按鈕是否亮起）、`_checkFloorDisplayShow`（樓層顯示），用 `reason` 參數讓迴圈中的失敗可以定位

## 二、設計考量與取捨

依主題分組。

### 目錄與命名

**`fakes/` 與 `mocks/` 為什麼分開放**
兩者替換的是不同的層：`fakes/` 在 app 自己的程式碼這一層換掉整個物件（`PanelPage` → `FakeSfxPlayer`，真正的 `SfxPlayer` 完全沒有執行）；`mocks/` 在最底層的 platform channel 攔截訊息（`SfxPlayer` → `AudioPlayer` → channel → 假的原生端，app 與套件的程式碼都照常執行）。放在一起會混淆「這個測試到底執行了哪些真實程式碼」。

**`MockAudioPlayersPlatform` 為什麼以「模擬的對象」命名，不以「被測的類別」命名**
它模擬的是 audioplayers 的原生端，跟被測的是 `SfxPlayer` 還是 `VoicePlayer` 無關，之後 `VoicePlayer` 的測試也可以沿用。

**`fakes/`、`mocks/` 為什麼放在 `test/` 而不是 `lib/`**
只有測試會用到，不應該被打包進 App。

### 替換方式的選擇

**什麼時候用依賴注入（`fakes/`），什麼時候用 mock channel（`mocks/`）**

| | 依賴注入（`FakeSfxPlayer`） | mock channel（`MockAudioPlayersPlatform`） |
|---|---|---|
| 被換掉的物件本身有沒有執行 | 沒有 | 有 |
| 能驗證送給原生端的內容（`audioFocus`、檔案路徑） | 不能 | 能 |
| 需要知道套件內部細節（channel 名稱、訊息格式） | 不需要 | 需要 |
| 套件升級時 | 不受影響 | 可能壞掉 |
| 與 `pump(Duration)` 虛擬時間的相容性 | 好 | 差（有真實的檔案 IO） |

- 被測對象本身跟原生端無關，只是透過依賴間接碰到原生端（例如 `PanelPage`）→ 用依賴注入換掉那個依賴。
- 被測對象本身就是直接跟原生端溝通的最後一層（例如 `SfxPlayer`）→ 在 platform channel 邊界攔截。

**`FakeSfxPlayer` 為什麼不模擬「播放中就丟棄」**
目前使用它的測試只需要知道「有沒有發出播放請求」，不需要測連續觸發的情境；等真的需要時再加。

**`FakeVoicePlayer` 為什麼用真正的 `Timer` 模擬播放時間，不是呼叫後立刻執行 `cb`**
`PanelPage` 的流程依賴「語音播完才開門」這個順序，立刻執行 `cb` 會把等待時間壓縮成零，驗證不到「有沒有真的等語音播完」。用 `Timer` 模擬後，`testWidgets` 的假時鐘可以用 `pump(Duration)` 精確推進到語音播完的那一刻。

**`FakeVolumeNotifier` 為什麼繼承真正的 `VolumeNotifier`，只覆寫 `build()`**
測試只需要控制初始狀態，`toggleSfx()`／`toggleVoice()` 沿用真正的實作，行為跟正式執行一致。代價是真正的 `build()` 預設值不會被這些測試執行到（詳見 `狀態管理結構.md`）。

### mock 的使用方式

**為什麼每個測試都建立新的 `MockAudioPlayersPlatform`，而不是共用一個再重設**
handler 註冊在 binding 的 messenger 上，同一個測試檔共用；如果共用同一個物件，舊測試留下的紀錄、已經兌現的 `Completer` 會影響下一個測試，造成假綠燈。每次建立新物件，欄位由語言保證是乾淨的，不會漏掉重設。建構子只建立乾淨的狀態，需要 `await` 或會改動全域狀態的準備工作放在 `init()`，清理放在 `dispose()`，並透過 `setUp`／`tearDown` 確保一定會執行（放在測試最後一行的話，`expect` 失敗時就不會執行）。

**mock 為什麼要記錄收到的呼叫，而不是只回覆 `null`**
只回覆 `null` 的 handler 會默默接住所有訊息，測試只能證明「沒有丟例外」。記錄呼叫之後，才能驗證 `SfxPlayer` 自己的責任：送出的 `audioFocus`、播放的檔案路徑、`resume` 的次數。套件內部決定送出的訊息（`init`、`create` 等）不做驗證，否則等於在替套件的內部實作把關。

**為什麼用 `waitForResume()` 這類等待訊號，而不是固定等待**
固定等待慢、不穩定，也看不出在等什麼；等到指定的呼叫抵達就往下走，`.timeout` 只是上限。驗證「沒發生」的情境沒有訊號可以等，才用固定等待。

## 三、撰寫測試的注意事項

**預期值要有獨立的來源**
如果預期值和實作都引用同一個常數或定義，定義寫錯時兩邊會一起錯，測試照樣通過（拿答案對答案）。因此：
- `timer_manager_test.dart` 的 `check constants` 把數值寫死、以 `設計主軸.md` 為準；`startTimer` 的測試才引用常數，守護「每種 `TimerType` 對應到自己的常數、單位正確」
- `floor_test.dart` 用公式與連續性檢查 `Floor` 的資料，不拿 `Floor` 自己來比對
- `sfx_player_test.dart` 的檔案路徑直接寫 `'sounds/panel/button.mp3'`、`audioFocus` 用 `AndroidAudioFocus.none.value`，不借用套件的計算邏輯產生預期值

**計時相關的測試要檢查邊界兩側**
只在觸發之後檢查，抓不到「太早觸發」的錯誤。因此差 1 毫秒確認還沒觸發、補 1 毫秒確認已觸發，兩側都要做反向驗證（故意改錯，確認測試真的會失敗）。

**驗證「沒發生」的測試一定要做反向驗證**
「沒發生」的測試很容易在錯誤的前提下通過：時間沒推進、等待不夠久，或流程根本沒走到，都會讓 callback「沒有觸發」。因此要先把前提寫出來，證明時間真的走到了該觸發的點（例如 `timer_manager_test.dart` 的 `clear()` 測試用 `async.elapsed` 確認時間），再故意改壞實作（例如清空 `clear()` 的內容），確認測試真的會失敗。
