# 畫面結構

本文件涵蓋 `screens/` 這一層——畫面組裝、業務邏輯、可變狀態，以及 `Navigator` 導覽切換，與 `資料結構.md`（`models/` + `styles/`，純資料/邏輯層）、`元件結構.md`（`widgets/`，可重用的純顯示元件）、`狀態管理結構.md`（`providers/`，Phase 16 新增，跨畫面共用狀態）互補（Phase 14 從原本同時涵蓋 `widgets/`＋`screens/` 兩層的 `元件結構.md` 拆分獨立而來，因為 `screens/` 之後幾個 Phase 的變動頻率會明顯比 `widgets/` 高）。格式比照其他文件，分兩個區域：

- **一、畫面速查**：開發中需要立即查詢的資訊——class 名稱、檔案位置、建構子參數、用途。只看目前的正確狀態，不含歷史沿革。
- **二、設計考量與取捨**：需要判斷「為什麼這樣拆」或評估是否要調整某個畫面時才需要查閱。同一個決定如果經過反覆調整，只保留「最後被捨棄的做法＋捨棄原因」與「最終定案＋定案理由」。

整體三層架構（`models/` / `widgets/` / `screens/`，另加獨立的 `styles/`）的完整說明見 `元件結構.md` 的「三層架構」小節；`providers/` 這第四層的說明見 `狀態管理結構.md`。

## 一、畫面速查

### HomePage（`screens/home_page.dart`）

App 的初始畫面（`MaterialApp.home`），主選單。Phase 16 起改成 `ConsumerWidget`（因為開關按鈕需要 `ref.watch(volumeProvider)` 顯示當下狀態），`build(BuildContext context, WidgetRef ref)`。`build()` 回傳 `Scaffold(body: SafeArea(child: Padding(padding: const EdgeInsets.all(20), child: Column(...))))`——沒有 `AppBar`，因此自己包一層 `SafeArea` 避開系統邊界（狀態列／底部手勢列，詳見下方設計考量）；外層再包一層 `Padding(all: 20)` 讓內容跟螢幕四邊保持間距，`Column` 的 `mainAxisAlignment` 設為 `MainAxisAlignment.start`，內容貼齊頂部（不垂直置中）。

`Column` 由上而下：兩顆進入模式的選單按鈕（各自間隔 `SizedBox(height: 10)`），再一個 `Row` 放兩顆音效／語音開關按鈕。

**選單按鈕**：透過頂層函式 `_getMenuButton(String title, String imgFile, VoidCallback onPressed)` 產生，本體是 `ElevatedButton`（`style: ElevatedButton.styleFrom(padding: EdgeInsets.zero)`，拿掉預設內距），`child` 是圖片化的按鈕內容：`Ink.image(image: AssetImage(imgFile), fit: BoxFit.cover, child: AspectRatio(aspectRatio: 2.4, child: Center(child: Text(title, style: TextStyle(color: LayoutCss.text1, fontSize: 30)))))`。`AspectRatio` 讓整塊圖片＋文字區域維持圖片原始比例；文字顏色沿用既有的 `styles/layout_css.dart` 裡的 `LayoutCss.text1`。之所以用 `Ink.image` 而不是 `Container` + `BoxDecoration(image: DecorationImage(...))`，是為了讓 `ElevatedButton` 點擊時的 Material 水波紋效果能正常顯示，詳見下方設計考量（Phase 15）。目前有兩顆：「面板模式」（`assets/images/home_page/normal.png`）與「動物模式」（`assets/images/home_page/animal.png`，Phase 16 先加上按鈕本身，`onPressed` 暫時也導向 `PanelPage`，真正的動物模式畫面待 Phase 17 建立）——兩者 `onPressed` 都呼叫 `Navigator.push(context, MaterialPageRoute(builder: (context) => const PanelPage()))` 跳轉。

**開關按鈕**：透過頂層函式 `_getVolumeButton(WidgetRef ref, VolumeType vType)` 產生 `VolumeButton`（`widgets/volume_button.dart`）：`isAllow` 用 `ref.watch(volumeProvider)` 依 `vType` 讀出 `isAllowSfx`／`isAllowVoice`（需要在狀態改變時重繪圖示，因此用 `watch`）；`onPressed` 直接在 closure 裡依 `vType` 呼叫 `ref.read(volumeProvider.notifier).toggleSfx()`／`toggleVoice()`（一次性動作，用 `read`，`ref` 透過閉包從 `_getVolumeButton` 的參數捕捉，不另外拆中介函式，詳見下方設計考量）。狀態定義詳見 `狀態管理結構.md`。

### PanelPage / _PanelPageState（`screens/panel_page.dart`，Phase 14 前叫 `MyHomePage`／`_MyHomePageState`，詳見下方設計考量）

電梯面板模式，透過 `HomePage` 的按鈕以 `Navigator.push` 進入的次要畫面。Phase 16 起 `PanelPage extends ConsumerStatefulWidget`、`_PanelPageState extends ConsumerState<PanelPage> with SingleTickerProviderStateMixin`（`ConsumerState` 一樣繼承自 `State`，`SingleTickerProviderStateMixin` 可以正常混入；`ref` 是 `ConsumerState` 內建的屬性，`build()` 簽名維持單一 `BuildContext` 參數，不像 `ConsumerWidget` 需要多帶一個 `WidgetRef` 參數，詳見 `狀態管理結構.md`），持有：

- 狀態欄位：`maxFloor`、`minFloor`、`floorMap`、`actionMap`、`_timerManager`、`elevator`、`_animateController`、`_animateOffset`、`_voicePlayer`（`late final VoicePlayer`，Phase 16 前叫 `_audioManager`／`AudioManager`）、`_sfxPlayer`（`late final SfxPlayer`，宣告方式與 `_voicePlayer` 一致）
- 生命週期：`initState()`（建立 `_animateController`、`_animateOffset`、`floorMap`、`actionMap`、`_voicePlayer`、`_sfxPlayer`）、`dispose()`（依序釋放 `_animateController`、`_voicePlayer`、`_sfxPlayer`，再呼叫 `super.dispose()`）
- `build(BuildContext context)`：依方向（直式／橫式）分派到 `_buildPortraitBody(this, context)` 或 `_buildLandscapeBody(this, context)`
- 業務邏輯方法：`goUpFloor`、`goDownFloor`、`moveFloor`、`switchDirectionOrIdle`、`hasTarget`、`setElevatorDirection`、`stopAnimate`、`openDoor`、`closeDoor`、`doOpenLongPressStart()`、`doOpenLongPressEnd()`。`moveFloor`／`openDoor`／`closeDoor` 都改呼叫 `requestVoicePlayer(...)`（不再直接呼叫 `_voicePlayer.request()`），詳見下方「業務邏輯與語音整合」小節
- 使用者互動的進入點方法：`floorTileOnTap(FloorButton myFloor, int btnIndex)`、`doorButtonOnTap(ActionButton actButton)`。原本還有一個 `volumeButtonOnPressed(VolumeType vType)`，Phase 16 隨著開關按鈕搬到 `HomePage`、`isAllow` 改由 `providers/volume.dart` 管理後整個移除。這幾個方法是 `shared.dart` 裡的 widget 組裝函式對外呼叫的入口，內部才真正呼叫 `setState()`，詳見下方「畫面元件與狀態變更的分工」設計考量、以及下方「按鈕音效與開關整合」小節
- 狀態管理包裝方法（Phase 16 新增）：`requestVoicePlayer({required String fileName, VoidCallback? cb})`、`requestSfxPlayer()`——分別讀取 `ref.read(volumeProvider)` 目前的 `isAllowVoice`／`isAllowSfx`，轉呼叫 `_voicePlayer.request(...)`／`_sfxPlayer.request(...)`，詳見 `狀態管理結構.md`

宣告 `part 'panel_page/landscape.dart';`、`part 'panel_page/portrait.dart';`、`part 'panel_page/shared.dart';`。只有這個檔案（主檔案）能宣告 `import`。

每次從 `HomePage` 透過 `Navigator.push` 進入，都是全新的 `PanelPage` 實例，電梯狀態會重置成初始狀態，不會保留上次離開時的樓層／按鈕選取狀態（Phase 14 決定，詳見下方設計考量）。

**portrait.dart**（`screens/panel_page/portrait.dart`，`part of` `panel_page.dart`）
直式版面組裝：`_buildPortraitBody`、`_portraitFloorScreen`、`_portraitButtonGrpBuiler`。`AppBar` 設定 `automaticallyImplyLeading: false`（見下方設計考量），`actions` 只放 `_getHomeButton(state)`——原本還有的兩顆音效／語音開關按鈕，Phase 16 起搬到 `HomePage`，這裡拿掉。

**landscape.dart**（`screens/panel_page/landscape.dart`，`part of` `panel_page.dart`）
橫式版面組裝：`_buildLandscapeBody`、`_landscapeFloorScreen`、`_landscapeButtonGrpBuilder`。右半邊區域上方的 `Row`（`mainAxisAlignment: MainAxisAlignment.end`，貼齊右上角）只放 `_getHomeButton(state)`（原因同上，開關按鈕搬到 `HomePage`），下方用 `Expanded` 包住原本的樓層按鈕格 `LayoutBuilder`。

**shared.dart**（`screens/panel_page/shared.dart`，`part of` `panel_page.dart`）
直式／橫式共用的 widget 組裝頂層函式：`_mainFloorScreen(state)`、`_getFloorTile(state, btnIndex)`、`_getDoorButton(state, actButton)`、`_getHomeButton(state)`。原本還有一個 `_getVolumeButton(state, vType)`，Phase 16 隨開關按鈕搬到 `HomePage` 一併移除。這些函式只負責組裝 widget、把互動 callback 接到 `_PanelPageState` 對應的方法上，本身不直接呼叫 `setState()`（原因見下方「畫面元件與狀態變更的分工」設計考量）。`_getHomeButton(state)` 只需要 `state`，內部用 `state.context`（`State` 內建的 `context` getter，跟 `widget` getter 是同樣的道理）呼叫 `Navigator.pop(state.context)`，不需要額外傳入 `BuildContext` 參數（詳見下方設計考量）；也刻意不呼叫 `_sfxPlayer.request()`，跟其他按鈕的音效回饋慣例不同，是刻意的決定（詳見下方設計考量），不是遺漏。

以上 part 檔案中的頂層函式，凡是需要存取 `_PanelPageState` 實例資料的，一律以明確參數 `state: _PanelPageState` 傳入（非隱式閉包捕捉）。

### 業務邏輯與語音整合（`screens/panel_page.dart`）

- **`stopAnimate()`**：新方法，內容是 `_animateController.stop(); _animateController.reset();`。從 `setElevatorDirection()` 裡抽出，讓「動畫該不該停」可以獨立於「`direction` 該不該變成 `idle`」被呼叫（見下方設計考量）。
- **`setElevatorDirection(Direction target)`**：`case Direction.idle` 分支改呼叫 `stopAnimate()`（原本直接寫 `_animateController.stop()`／`.reset()`，行為不變，純粹抽方法）。
- **`moveFloor(int moveIndex, void Function() goNextFloor)`**：到達目標樓層的分支裡，`setState()` 只窄地包住 `elevator.currentFloor` 的更新；接著（在 `setState()` 之外）依序呼叫 `requestVoicePlayer(fileName: 'sounds/ding.mp3', cb: stopAnimate)` 與 `requestVoicePlayer(fileName: floorMap[elevator.currentFloor]!.audioFile, cb: ...)`——樓層語音的 callback 裡才真正用 `setState()` 執行 `setElevatorDirection(Direction.idle)` 與 `floorMap[elevator.currentFloor]!.isTarget = false`，然後呼叫 `openDoor()`。
- **`openDoor()`**：guard 判斷通過後，`setState()` 把 `doorStatus` 改成 `opening`、`_animateController.repeat()`；接著呼叫 `requestVoicePlayer(fileName: actionMap[ActionType.open]!.audioFile)`（開門語音，跟開門動畫同時進行，不等語音播完）；`_timerManager.startTimer(TimerType.doorProc, ...)` 沿用原本邏輯，時間到才真正轉成 `open`。
- **`closeDoor()`**：一進入就先呼叫 `requestVoicePlayer(fileName: actionMap[ActionType.close]!.audioFile)`，再 `setState()` 把 `doorStatus` 改成 `closing`、開始動畫，其餘沿用原本邏輯。

### 按鈕音效與開關整合（`screens/panel_page.dart`）

- **`floorTileOnTap(FloorButton myFloor, int btnIndex)`**：一進入就呼叫 `requestSfxPlayer()`（不論後續業務邏輯是否真的觸發電梯移動，按下去都要有音效回饋），再執行原本樓層按鈕的業務邏輯（`isTarget` 切換、視情況觸發 `goUpFloor`/`goDownFloor`）。
- **`doorButtonOnTap(ActionButton actButton)`**：同樣先呼叫 `requestSfxPlayer()`，再依 `actButton.btnType` 呼叫 `openDoor()`/`closeDoor()`；即使 `openDoor()`/`closeDoor()` 內部 guard 判斷後沒有實際動作，音效仍會播放。
- **`requestVoicePlayer({required String fileName, VoidCallback? cb})`／`requestSfxPlayer()`**（Phase 16 新增）：分別讀取 `ref.read(volumeProvider).isAllowVoice`／`.isAllowSfx`，轉呼叫 `_voicePlayer.request(isAllow: ..., fileName: fileName, cb: cb)`／`_sfxPlayer.request(isAllow: ...)`。用 `ref.read()` 而非 `ref.watch()`，因為這是事件處理當下的一次性讀取，不需要訂閱、不需要因此重建畫面（詳見 `狀態管理結構.md`）。

App 進入點。`void main() { runApp(const ProviderScope(child: MyApp())); }`（Phase 16 起 `runApp` 包一層 `ProviderScope`，整個 App 只需要這一份容器）＋ `class MyApp extends StatelessWidget`。`MaterialApp.home` 指向 `const HomePage()`（Phase 14 前直接指向 `MyHomePage`）。

## 二、設計考量與取捨

**`AppBar` 曾經嘗試包成獨立的 `PortraitAppBar` widget，最後放棄**
`Scaffold.appBar` 要求 `PreferredSizeWidget` 介面，包成獨立 widget 需要多寫 `implements PreferredSizeWidget` ＋ `preferredSize` getter。評估這層額外成本換來的效益不高，最後決定不抽，直接在畫面組裝處寫 `AppBar(...)`。

**`AnimationController` 為什麼留在 `_PanelPageState`，只把算好的 `Animation<Offset>` 傳給 `DirectionIcon`**
`SlideTransition` 之類的動畫 widget 直接訂閱（listen）傳入的 `Animation` 物件本身即可局部重繪，不需要透過外層 `setState()`。顯示端只需要已經算好的 `Animation<Offset>`，不需要碰到原始 `Controller`；`Controller` 的啟動／停止仍由業務邏輯方法呼叫，留在 `_PanelPageState`（詳見 `資料結構.md` 的 `AnimateOffset` 段落）。

**橫式／直式版面為什麼用 `part`/`part of`，不是各自抽成獨立 `StatelessWidget`**
評估後兩個版面各自的組裝邏輯抽成 class 效益不高（不需要 `const` 優化、不會被其他畫面重用），但兩份程式碼混在同一個檔案中難以管理。Dart 的 private 存取權限以「檔案所屬 library」為界，`_PanelPageState` 本身是私有 class，plain `import` 無法跨檔案存取，`extension`/`mixin` 也一樣受限；因此改用 `part`/`part of` 機制，讓多個實體檔案共用同一個 library 的私有存取權限。只有主檔案（`panel_page.dart`）能宣告 `import`，part 檔案不能有自己的 import。

**檔案結構：`screens/panel_page.dart` + `screens/panel_page/portrait.dart` + `screens/panel_page/landscape.dart` + `screens/panel_page/shared.dart`**
曾考慮 `screens/panel_page/main.dart` 的替代方案，但為避免跟真正的 App 進入點 `lib/main.dart` 混淆而放棄（Phase 14 把主檔案跟 `part` 檔案所在資料夾從 `home_page` 一併改名成 `panel_page` 時，這個考量依然成立）。`shared.dart` 用來存放直式／橫式都共用、且不需要呼叫 `setState()` 的 widget 組裝頂層函式（例如 `_mainFloorScreen`），避免同一份組裝邏輯在 `portrait.dart`／`landscape.dart` 各寫一份。

**畫面元件與狀態變更的分工：為什麼 `shared.dart`／`portrait.dart`／`landscape.dart` 裡的頂層函式不直接呼叫 `setState()`**
Flutter 的 `State.setState()` 被標記為 `@protected`——只能在該 `State` 自己的實例方法（或子類別）裡呼叫。在 class 外部呼叫，雖然因為 `part`/`part of` 給的存取權限技術上可行（能編譯、能執行），仍會被靜態分析器標記警告，違反框架原本「`setState()` 只給 `State` 自己用」的設計意圖。因此把「會呼叫 `setState()` 的邏輯」都留在 `_PanelPageState` 自己的方法裡（`floorTileOnTap`、`doorButtonOnTap`、`volumeButtonOnPressed`），`shared.dart`／`portrait.dart`／`landscape.dart` 裡的頂層函式只負責組裝 widget、把 callback 接到這些方法上，不直接碰 `setState()`。兩者職責分得更乾淨：頂層函式只管「畫面長什麼樣子」，`_PanelPageState` 自己的方法管「狀態怎麼變」。

**Race condition：語音播放期間點擊其他樓層按鈕，會繞過開關門流程直接觸發移動**
`moveFloor` 到達目標樓層時，原本 `setElevatorDirection(Direction.idle)` 是立即同步執行的。後來把 `openDoor()` 延後到語音（`ding` + 樓層語音）播放完成後才觸發，導致「電梯已抵達（`direction == idle`），但語音還在播放、`doorStatus` 還沒真的變成 `opening`（仍是 `closed`）」這段空窗期出現——而這個狀態組合（`direction == idle && doorStatus == closed`），跟「電梯已經完整跑完一輪開關門、真正閒置」的狀態組合完全相同，導致樓層按鈕 `onTap` 的判斷式誤判，繞過開關門流程直接觸發 `goUpFloor()`/`goDownFloor()`。

修正前曾考慮兩個方向：(1) 新增一個獨立旗標專門標記「語音播報流程還沒跑完」；(2) 把 `setElevatorDirection(Direction.idle)` 延後到語音播放完成的 callback 裡才執行，讓 `direction` 跟 `doorStatus` 的轉變綁在同一個 `setState()` 裡、永遠同步變化，不會再出現中間態。最終選擇方向 (2)，理由是不想再引入一個語意上跟 `idle` 太接近、容易混淆的新欄位；曾嘗試過「借用 `floorMap[currentFloor].isTarget` 是否已被清除」當作替代判斷依據，但發現 `onTap` 一開始就會無條件 toggle 被點擊樓層的 `isTarget`，跟這個欄位本身「使用者想不想去這層樓」的語意耦合在一起，容易在邊界情況出包，因此放棄，改採方向 (2)。

**動畫停止時機為什麼要獨立成 `stopAnimate()`，不直接綁在 `direction` 變成 `idle` 的那一刻**
上述修正的副作用：`direction` 現在要撐到語音全部播完才變成 `idle`，如果動畫的停止／重置也跟著綁在同一時間點，會讓使用者「已經聽到語音」但視覺上「方向箭頭動畫看起來還在移動」，聽覺跟視覺不同步、體感上有點怪。解法是把 `_animateController.stop()`／`.reset()` 抽成獨立的 `stopAnimate()` 方法，讓「動畫該不該停」這個純視覺層面的決定，可以跟「`direction` 該不該變成 `idle`」這個業務邏輯層面的決定分開判斷——`stopAnimate()` 改成在 `ding` 音效播放完成的當下就呼叫（比樓層語音、`direction` 轉變都早），讓動畫更早停下來，聽覺與視覺的同步感更好。這個 callback 不需要包 `setState()`，因為 `AnimationController` 的變化是被動畫 widget 直接訂閱（listen）的，跟 `AnimateOffset` 原本的設計理由一致（詳見 `資料結構.md`）；但另一個會動到 `direction`／`isTarget` 的 callback，因為是普通欄位，仍然需要包 `setState()` 才能通知 Flutter 重繪。

**為什麼原本的 `MyHomePage` 改名為 `PanelPage`，新增獨立的 `HomePage` 當主選單（Phase 14）**
Phase 14 之前，電梯面板模式直接是 `MaterialApp.home`，沿用 `flutter create` 範本留下的 `MyHomePage` 這個名字。新增主選單畫面後，「Home」這個語意上應該屬於真正的 App 入口（主選單），因此原本的面板模式畫面改名為 `PanelPage`——呼應 `models/panel_buttons.dart`（Phase 13 已經把 `panel` 這個字定為「電梯操作面板」領域概念的用詞）；`MyHomePage` 這個名字讓給新的主選單畫面，同時拿掉 `flutter create` 範本留下的 `My` 前綴，簡化成 `HomePage`。兩個畫面都統一用 `Page` 尾綴（Flutter 常見的三種尾綴慣例：`Page`／`Screen`／`View`，擇一後全專案統一，`Page` 是延續專案原有慣例、摩擦最小的選擇）。

**主選單這次沒有放動物模式按鈕／音效語音開關（Phase 14）**
`設計主軸.md` 的主選單 UI 元件清單雖然已經列了動物模式按鈕、動物語音互動開關、音效／語音開關，但動物模式功能本身要到 Phase 17、18 才實作，音效／語音狀態要跨 `HomePage`／`PanelPage` 共用也要等 Phase 16 導入 `Provider`/`Riverpod` 時才處理。這次評估沒有必要提前設計這兩塊，決定 `HomePage` 這次只放「進入面板模式」一顆按鈕，`_sfxPlayer`／`_audioManager` 維持只屬於 `_PanelPageState`，避免過度設計。

**`Navigator.push` 進入面板模式時，電梯狀態要不要保留（Phase 14）**
`Navigator.push` 每次呼叫都是建立全新的 `PanelPage` 實例與 `State`；從主選單重新進入面板模式時，決定讓電梯重置回初始狀態（樓層、按鈕選取狀態都不保留），不特別設計保留機制（例如用 `IndexedStack` 讓兩個畫面同時存活）。評估這個 App 情境下沒有保留上次狀態的必要，維持「每次重新開始」更單純。

**`_getHomeButton` 為什麼只傳 `state`，不額外傳 `BuildContext`（Phase 14）**
跟 `State<T>` 內建的 `widget` getter 是同樣的道理——`State` 本身就內建一個 `context` getter，`state.context` 拿到的就是同一個 `BuildContext`，不需要另外用參數重複傳遞一份。因此 `_getHomeButton(state)` 只需要 `state`，內部用 `Navigator.pop(state.context)`，簽名也跟其他頂層函式（`_getVolumeButton(state, vType)` 等）保持一致。

**`PanelPage` 的 `AppBar` 為什麼設定 `automaticallyImplyLeading: false`（Phase 14）**
`AppBar` 預設行為：沒有明確設定 `leading`、且 `Navigator.canPop(context)` 為 `true` 時，會自動在 `leading` 插入一顆返回箭頭（等同 `Navigator.pop`）。`PanelPage` 在 Phase 14 之前是 `MaterialApp.home`（堆疊最底層，無法 `pop`），這個自動行為沒有出現過；改成被 `push` 進來的次要畫面後，這個條件成立，自動跳出的返回箭頭跟自己刻的 `_getHomeButton`（`actions` 裡的 home 圖示）功能重複，因此設定 `automaticallyImplyLeading: false` 關閉自動行為，只保留自訂的 home 按鈕。橫式版面本來就沒有用到 `AppBar`，不受影響。

**這次沒有為 `Navigator` 額外包一層路由／工具檔案（Phase 14）**
評估目前只有 `HomePage`、`PanelPage` 兩個畫面，導覽方式單純（直接 `push`/`pop`，沒有具名路由、沒有條件式導覽邏輯），`Navigator` 本身已經是現成的工具，額外抽一層檔案（例如集中管理路由的 `router.dart`）看不出效益。等後續畫面數量與導覽複雜度增加（例如 Phase 17 動物模式）後，可以重新評估。

**`HomePage` 按鈕從純文字改成圖片化，最終沒有用 `Container` + `BoxDecoration(image: DecorationImage(...))`，改用 `Ink.image`（Phase 15）**
一開始用 `Container` + `BoxDecoration(image: DecorationImage(...))` 當 `ElevatedButton` 的 `child` 顯示底圖，功能上（圖片顯示、`AspectRatio` 控制比例）沒問題，但發現點擊按鈕時 Material 的水波紋效果完全看不到。原因是 `ElevatedButton` 內部的 `Material`＋`InkWell` 繪製水波紋時，順序是「先畫水波紋、後畫傳入的 `child`」；`Container` 畫出的不透明圖片剛好蓋滿整個按鈕範圍，會在水波紋之後才畫上去，直接蓋住底下的水波紋。改用 `Ink.image`（API 跟 `Container`/`DecorationImage` 幾乎一樣，但裝飾是直接畫進最近的 `Material` 畫布本身，而不是獨立的一塊畫布）解決，水波紋能正常疊加顯示在圖片上。

**`HomePage` 按鈕圖片使用真實美術素材，不是預留位置（Phase 15）**
`Image`／`AssetImage` 語法練習不需要真的等到正式美術才能進行，但這次學習者已經準備好實際要用的 PNG（面板模式按鈕的底圖，含裝飾用樓層圓形圖示與葉子的橫幅插畫），因此直接用這張圖走完整流程，不另外用色塊或系統圖示當預留位置練習。圖片格式確認是 PNG（點陣圖），因此直接用 `Image`/`AssetImage` 家族處理即可，不需要額外引入 `flutter_svg`。

**`HomePage` 按鈕圖片上要疊文字時，為什麼選 `Container`/`Ink.image` 直接當文字的父層，而不是用 `Stack` + `Positioned`（Phase 15）**
文字需求只是「固定置中」，不需要之後在圖片特定位置（例如偏下方）疊加其他裝飾元素的彈性，因此評估 `Stack`＋`Positioned` 的額外彈性這次用不到，選擇比較單純的做法：圖片元件（`Ink.image`）直接把文字當 `child`（搭配 `Center`），文字自然疊在圖片正中央。之後如果有偏移定位的需求，再改用 `Stack`。

**`HomePage` 按鈕保留 `ElevatedButton`，沒有改用 `GestureDetector` 自己組裝外觀（Phase 15）**
圖片化之後，如果改用 `GestureDetector` + 純手勢偵測，需要自己刻按壓視覺回饋（例如透明度變化），且會失去 `ElevatedButton` 內建的 Material 水波紋效果。評估這次沒有客製化外觀（例如非矩形形狀）的強烈需求，選擇沿用 `ElevatedButton`，用 `style: ElevatedButton.styleFrom(padding: EdgeInsets.zero)` 拿掉預設內距，讓圖片可以貼齊按鈕邊緣，同時保留現成的水波紋回饋（搭配 `Ink.image` 解決水波紋被圖片蓋住的問題，見上一則設計考量）。

**Phase 16：音效／語音開關按鈕為什麼從 `PanelPage` 搬到 `HomePage`，而不是兩邊都保留**
`isAllow` 狀態要跨 `HomePage`／`PanelPage`（未來還有動物模式畫面）共用後，統一只在一個畫面顯示與操作，比兩邊都放一份更不容易讓使用者混淆「同一個開關到底在哪裡調」。評估後決定把開關按鈕整個收斂到 `HomePage`（主選單），`PanelPage` 的 `AppBar` 不再顯示這兩顆按鈕，`portrait.dart`／`landscape.dart`／`shared.dart` 裡對應的 `_getVolumeButton` 呼叫與函式本身一併移除。

**Phase 16：`PanelPage` 呼叫 `request()` 前為什麼多包一層 `requestVoicePlayer()`／`requestSfxPlayer()`，不直接在五個呼叫點各自寫 `ref.read(volumeProvider)...`**
`floorTileOnTap`、`doorButtonOnTap`、`moveFloor`、`openDoor`、`closeDoor` 都需要在呼叫 `_voicePlayer.request()`／`_sfxPlayer.request()` 前讀一次目前的 `isAllow` 值，各自重複寫 `ref.read(volumeProvider)...` 會很囉唆。抽成 `_PanelPageState` 自己的兩個方法，呼叫端只需要記得呼叫 `requestVoicePlayer(fileName: ..., cb: ...)`／`requestSfxPlayer()`，讀取共用狀態這件事集中在一個地方維護。

**Phase 16：`HomePage` 為什麼是 `ConsumerWidget`，`PanelPage` 為什麼是 `ConsumerStatefulWidget`**
`HomePage` 上的開關按鈕需要「顯示目前的開關狀態」，圖示要在狀態改變時正確重繪，因此需要 `ref.watch(volumeProvider)`；`HomePage` 本身沒有其他需要跨越多次 `build()` 存活的可變狀態，維持 `Stateless` 的寫法即可，只換成 `ConsumerWidget`。`PanelPage` 因為已經有大量既有的 `StatefulWidget` 邏輯（電梯狀態機、動畫控制器等），維持 `StatefulWidget` 的殼、換成 `ConsumerStatefulWidget`／`ConsumerState` 取得 `ref`；且 `PanelPage` 拿掉開關按鈕後只需要在動作當下一次性讀取 `isAllow`（`ref.read()`），不需要因為這份狀態改變而重建整個畫面。

**Phase 16：`HomePage` 的 `_getVolumeButton`，為什麼把切換邏輯直接寫進 `onPressed` closure，不另外拆一個 `volumeButtonOnPressed` 函式**
`PanelPage` 原本的 `volumeButtonOnPressed(VolumeType vType)` 是 `_PanelPageState` 的實例方法，可以直接存取 `_PanelPageState` 的欄位。搬到 `home_page.dart` 後如果比照寫成一個獨立的頂層函式，這個函式本身沒有 `ref` 可以用（`ref` 是 `_getVolumeButton` 的參數，不會自動傳遞給另一個獨立函式），還要額外設計怎麼把 `ref` 傳進去。評估後決定不拆這個中介函式，直接把兩行判斷寫進 `onPressed` 的 closure 裡，透過閉包直接捕捉外層 `_getVolumeButton(WidgetRef ref, VolumeType vType)` 已有的 `ref`，減少一層不必要的參數傳遞。
