# 元件結構

本文件涵蓋 `widgets/` 與 `screens/` 兩層（畫面組裝與可重用顯示元件），與 `資料結構.md`（`models/` + `styles/`，純資料/邏輯層）互補。格式比照 `資料結構.md`，分兩個區域：

- **一、元件速查**：開發中需要立即查詢的資訊——class 名稱、檔案位置、建構子參數、用途。只看目前的正確狀態，不含歷史沿革。
- **二、設計考量與取捨**：需要判斷「為什麼這樣拆」或評估是否要調整某個元件時才需要查閱。同一個決定如果經過反覆調整，只保留「最後被捨棄的做法＋捨棄原因」與「最終定案＋定案理由」。

## 一、元件速查

### widgets/（StatelessWidget，純顯示、不含業務邏輯）

**ArrowIcon**（`widgets/arrow_icon.dart`）
依 `directionIcon: ScreenIcon`（final）決定顯示哪個方向的箭頭圖示，回傳 `FittedBox(child: Icon(...))`。

**DoorButton**（`widgets/door_button.dart`）
開/關門按鈕。參數：`actionButton: ActionButton`（final）＋ 6 個 `VoidCallback?`：`onPointerDown`、`onPointerUp`、`onPointerCancel`、`onTap`、`onLongPressStart`、`onLongPressEnd`。內部用 `Listener` + 手勢偵測包裝，對外一律用不帶參數的 `VoidCallback?`。

**FloorTile**（`widgets/floor_tile.dart`）
樓層按鈕。參數：`floorButton: FloorButton`（final）＋ `onTap: VoidCallback?`。

**DirectionIcon**（`widgets/direction_icon.dart`）
樓層顯示區的方向箭頭（含滑動動畫）。參數：`elevator: Elevator`（final）＋ `animateOffset: AnimateOffset`（final）。依 `elevator.direction`／`elevator.doorStatus` 決定要用 `animateOffset` 的哪個 `Animation<Offset>` 包在 `SlideTransition` 裡，並顯示對應的 `ArrowIcon`。

**FloorDisplay**（`widgets/floor_display.dart`）
樓層數字顯示區整體。參數：`elevator: Elevator`、`animateOffset: AnimateOffset`、`floorText: String`。組合 `DirectionIcon` ＋ 樓層文字（`Expanded` + `FittedBox` + `Text`）。

### screens/（畫面組裝＋業務邏輯＋可變狀態）

**MyHomePage / _MyHomePageState**（`screens/home_page.dart`）
唯一的 `StatefulWidget`。`_MyHomePageState extends State<MyHomePage> with SingleTickerProviderStateMixin`，持有：

- 狀態欄位：`maxFloor`、`minFloor`、`floorMap`、`actionMap`、`_timerManager`、`elevator`、`_animateController`、`_animateOffset`
- 生命週期：`initState()`（建立 `_animateController`、`_animateOffset`、`floorMap`、`actionMap`）、`dispose()`
- `build()`：依方向（直式／橫式）分派到 `_buildPortraitBody(this, context)` 或 `_buildLandscapeBody(this, context)`
- 畫面組裝輔助方法：`_mainFloorScreen()`（回傳 `FloorDisplay(...)`）、`_getFloorTile(int btnIndex)`、`_getDoorButton(ActionButton actButton)`（回傳 `DoorButton(...)`）
- 業務邏輯方法（與元件化無關，維持原樣）：`goUpFloor`、`goDownFloor`、`moveFloor`、`switchDirectionOrIdle`、`hasTarget`、`setElevatorDirection`、`openDoor`、`closeDoor`、`doOpenLongPressStart()`、`doOpenLongPressEnd()`

宣告 `part 'home_page/portrait.dart';` 與 `part 'home_page/landscape.dart';`。只有這個檔案（主檔案）能宣告 `import`。

**portrait.dart**（`screens/home_page/portrait.dart`，`part of` `home_page.dart`）
直式版面組裝：`_buildPortraitBody`、`_portrailFloorScreen`、`_portraitButtonGrpBuiler`。AppBar 直接用 `const AppBar(...)` 內嵌在組裝邏輯裡，沒有獨立成 widget。

**landscape.dart**（`screens/home_page/landscape.dart`，`part of` `home_page.dart`）
橫式版面組裝：`_buildLandscapeBody`、`_landscapeFloorScreen`、`_landscapeButtonGrpBuilder`。

以上 part 檔案中的頂層函式，凡是需要存取 `_MyHomePageState` 實例資料的，一律以明確參數 `state: _MyHomePageState` 傳入（非隱式閉包捕捉）。

**MyApp**（`lib/main.dart`）
App 進入點。`void main() { runApp(const MyApp()); }` ＋ `class MyApp extends StatelessWidget`。

## 二、設計考量與取捨

**三層架構：`models/` / `widgets/` / `screens/`（另加獨立的 `styles/`）**
`models/` 是純資料／邏輯物件；`widgets/` 是可重用的顯示元件（`StatelessWidget`，不含業務邏輯）；`screens/` 負責把 `widgets/` 組裝成完整畫面、並持有業務邏輯與可變狀態（`_MyHomePageState`）。`styles/` 特意獨立於 `models/` 之外，避免跟 Flutter 自己的 `Theme`/`ThemeData` 概念語意衝突。

**為什麼把「回傳 Widget 的方法」抽成獨立的 `StatelessWidget` class，而不是留在 `_MyHomePageState` 裡當方法**
獨立成 class 可以標記 `const`（減少不必要的重建）、在 DevTools 的 Widget Tree 中會是獨立節點方便除錯定位、建構子參數是明確的依賴注入，不像方法用閉包隱式讀取外層 state 欄位。

**抽取優先順序，依複雜度分級**
第一級：純粹「輸入→輸出」、不需要 callback（例：`ArrowIcon`）最先抽。第二級：需要透過建構子傳入 callback（例：`DoorButton`、`FloorTile`）。第三級：需要共用 `AnimationController`／動畫狀態（例：`DirectionIcon`、`FloorDisplay`）最後處理，且需要額外設計「Controller 留在哪裡」。

**AppBar 曾經嘗試包成獨立的 `PortraitAppBar` widget，最後放棄**
`Scaffold.appBar` 要求 `PreferredSizeWidget` 介面，包成獨立 widget 需要多寫 `implements PreferredSizeWidget` ＋ `preferredSize` getter。評估這層額外成本換來的效益不高，最後決定不抽，直接在畫面組裝處寫 `const AppBar(...)`。

**`DoorButton` 對外只用不帶參數的 `VoidCallback?`，不直接暴露 `Listener` 原生的 `PointerDownEvent` 等事件型別**
檢查過實際呼叫端，從未用到事件參數本身；暴露原始事件型別只是徒增外部依賴、沒有實際使用需求。內部用 lambda 把原生事件包一層再轉呼叫 `VoidCallback?`。

**`AnimationController` 為什麼留在 `_MyHomePageState`，只把算好的 `Animation<Offset>` 傳給 `DirectionIcon`**
`SlideTransition` 之類的動畫 widget 直接訂閱（listen）傳入的 `Animation` 物件本身即可局部重繪，不需要透過外層 `setState()`。顯示端只需要已經算好的 `Animation<Offset>`，不需要碰到原始 `Controller`；`Controller` 的啟動／停止仍由業務邏輯方法呼叫，留在 `_MyHomePageState`（詳見 `資料結構.md` 的 `AnimateOffset` 段落）。

**`DirectionIcon` 為什麼傳入整個 `Elevator` 物件，而不是只傳 `Direction`／`DoorStatus` 兩個欄位**
明知道傳整個物件耦合度較鬆，但考量呼叫端比較方便、不用逐一挑欄位，故意接受這個取捨。

**命名規則：避免 `models/` 跟 `widgets/` 撞名**
model 用領域概念命名（`FloorButton`、`ActionButton`），widget 用 UI／視覺角色命名，字彙盡量貼近 Flutter 自己既有 widget 的命名習慣（`Tile`、`Card`、`Chip`、`Bar`、`Panel`、`Icon`、`Button`、`View`）。例如資料是 `FloorButton`，畫面元件是 `FloorTile`；資料是 `ActionButton`，畫面元件是 `DoorButton`；純顯示用的圖示邏輯是 `ArrowIcon`。真的無法避免撞名時，退而求其次用 `import '...' as prefix;` 做區隔。

**橫式／直式版面為什麼用 `part`/`part of`，不是各自抽成獨立 `StatelessWidget`**
評估後兩個版面各自的組裝邏輯抽成 class 效益不高（不需要 `const` 優化、不會被其他畫面重用），但兩份程式碼混在同一個檔案中難以管理。Dart 的 private 存取權限以「檔案所屬 library」為界，`_MyHomePageState` 本身是私有 class，plain `import` 無法跨檔案存取，`extension`/`mixin` 也一樣受限；因此改用 `part`/`part of` 機制，讓多個實體檔案共用同一個 library 的私有存取權限。只有主檔案（`home_page.dart`）能宣告 `import`，part 檔案不能有自己的 import。

**檔案結構：`screens/home_page.dart` + `screens/home_page/portrait.dart` + `screens/home_page/landscape.dart`**
曾考慮 `screens/home_page/main.dart` 的替代方案，但為避免跟真正的 App 進入點 `lib/main.dart` 混淆而放棄。

**`ActionButton.isPressed` 是否該改成 `StatefulWidget` 自己管理的 local state**
評估後這個 app 規模小，效能差異幾乎無感，但仍是值得養成的好習慣模式。決定延後處理，已列入 `學習路徑總覽.md` 中 Phase 11 之後的學習計畫，此處不重複記錄理由。
