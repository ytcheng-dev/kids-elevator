# 元件結構

本文件涵蓋 `widgets/` 與 `screens/` 兩層（畫面組裝與可重用顯示元件），與 `資料結構.md`（`models/` + `styles/`，純資料/邏輯層）互補。格式比照 `資料結構.md`，分兩個區域：

- **一、元件速查**：開發中需要立即查詢的資訊——class 名稱、檔案位置、建構子參數、用途。只看目前的正確狀態，不含歷史沿革。
- **二、設計考量與取捨**：需要判斷「為什麼這樣拆」或評估是否要調整某個元件時才需要查閱。同一個決定如果經過反覆調整，只保留「最後被捨棄的做法＋捨棄原因」與「最終定案＋定案理由」。

## 一、元件速查

### widgets/（StatelessWidget，純顯示、不含業務邏輯）

**ArrowIcon**（`widgets/arrow_icon.dart`）
依 `directionIcon: ScreenIcon`（final）決定顯示哪個方向的箭頭圖示，回傳 `FittedBox(child: Icon(...))`。

**DoorButton**（`widgets/door_button.dart`）
開/關門按鈕。參數：`actionButton: ActionButton`（final）＋ 6 個 `VoidCallback?`：`onPointerDown`、`onPointerUp`、`onPointerCancel`、`onTap`、`onLongPressStart`、`onLongPressEnd`。內部用 `Listener` + 手勢偵測包裝，對外一律用不帶參數的 `VoidCallback?`。

**FloorTile**（`widgets/floor_tile.dart`）
樓層按鈕。參數：`floorButton: FloorButton`（final）＋ `onTap: VoidCallback?`。

**DirectionIcon**（`widgets/direction_icon.dart`）
樓層顯示區的方向箭頭（含滑動動畫）。參數：`elevator: Elevator`（final）＋ `animateOffset: AnimateOffset`（final）。依 `elevator.direction`／`elevator.doorStatus` 決定要用 `animateOffset` 的哪個 `Animation<Offset>` 包在 `SlideTransition` 裡，並顯示對應的 `ArrowIcon`。

**FloorDisplay**（`widgets/floor_display.dart`）
樓層數字顯示區整體。參數：`elevator: Elevator`、`animateOffset: AnimateOffset`、`floorText: String`。組合 `DirectionIcon` ＋ 樓層文字（`Expanded` + `FittedBox` + `Text`）。

**VolumeButton**（`widgets/volume_button.dart`）
音效／語音開關按鈕。參數：`volumeType: VolumeType`（final）、`isAllow: bool`（final）、`onPressed: VoidCallback?`。依 `volumeType` 決定使用哪一組圖示（`sfx`：`Icons.volume_up`/`Icons.volume_off`；`voice`：`Icons.music_note`/`Icons.music_off`），再依 `isAllow` 決定顯示開或關的圖示，回傳 `IconButton(icon: Icon(icon), onPressed: onPressed)`。

### screens/（畫面組裝＋業務邏輯＋可變狀態）

**MyHomePage / _MyHomePageState**（`screens/home_page.dart`）
唯一的 `StatefulWidget`。`_MyHomePageState extends State<MyHomePage> with SingleTickerProviderStateMixin`，持有：

- 狀態欄位：`maxFloor`、`minFloor`、`floorMap`、`actionMap`、`_timerManager`、`elevator`、`_animateController`、`_animateOffset`、`_audioManager`（`late final AudioManager`）、`_sfxPlayer`（`late final SfxPlayer`，宣告方式與 `_audioManager` 一致）
- 生命週期：`initState()`（建立 `_animateController`、`_animateOffset`、`floorMap`、`actionMap`、`_audioManager`、`_sfxPlayer`）、`dispose()`（依序釋放 `_animateController`、`_audioManager`、`_sfxPlayer`，再呼叫 `super.dispose()`）
- `build()`：依方向（直式／橫式）分派到 `_buildPortraitBody(this, context)` 或 `_buildLandscapeBody(this, context)`
- 業務邏輯方法：`goUpFloor`、`goDownFloor`、`moveFloor`、`switchDirectionOrIdle`、`hasTarget`、`setElevatorDirection`、`stopAnimate`（從 `setElevatorDirection` 抽出，見下方設計考量）、`openDoor`、`closeDoor`、`doOpenLongPressStart()`、`doOpenLongPressEnd()`。`moveFloor`／`openDoor`／`closeDoor` 都整合了 `_audioManager.request()` 呼叫，詳見下方「業務邏輯與語音整合」小節
- 使用者互動的進入點方法：`floorTileOnTap(FloorButton myFloor, int btnIndex)`、`doorButtonOnTap(ActionButton actButton)`、`setDoorButtonPressed(ActionButton actButton, bool isPressed)`、`volumeButtonOnPressed(VolumeType vType)`。這幾個方法是 `shared.dart` 裡的 widget 組裝函式對外呼叫的入口，內部才真正呼叫 `setState()`，詳見下方「畫面元件與狀態變更的分工」設計考量、以及下方「按鈕音效與開關整合」小節

宣告 `part 'home_page/landscape.dart';`、`part 'home_page/portrait.dart';`、`part 'home_page/shared.dart';`。只有這個檔案（主檔案）能宣告 `import`。

**portrait.dart**（`screens/home_page/portrait.dart`，`part of` `home_page.dart`）
直式版面組裝：`_buildPortraitBody`、`_portraitFloorScreen`、`_portraitButtonGrpBuiler`。`AppBar` 的 `actions` 放兩個 `VolumeButton`（`_getVolumeButton(state, VolumeType.sfx)`／`_getVolumeButton(state, VolumeType.voice)`）。

**landscape.dart**（`screens/home_page/landscape.dart`，`part of` `home_page.dart`）
橫式版面組裝：`_buildLandscapeBody`、`_landscapeFloorScreen`、`_landscapeButtonGrpBuilder`。右半邊區域（原本直接放樓層按鈕格的 `Expanded`）改包一層 `Column`：上方是 `Row`（`mainAxisAlignment: MainAxisAlignment.end`，放兩個 `VolumeButton`，貼齊右上角——`Row` 的 `mainAxisSize` 預設為 `max`，即使 `Column` 的 `crossAxisAlignment` 是預設的 `center`，`Row` 仍會撐滿可用寬度，`mainAxisAlignment: end` 才能生效），下方用 `Expanded` 包住原本的樓層按鈕格 `LayoutBuilder`，讓按鈕格吃掉扣除控制列後的剩餘空間。`_landscapeButtonGrpBuilder` 本身不需要因此調整內部尺寸計算，因為它是透過 `LayoutBuilder` 讀取實際被分配到的 `constraints`，約束的變化會自動反映，不需要額外處理。

**shared.dart**（`screens/home_page/shared.dart`，`part of` `home_page.dart`）
直式／橫式共用的 widget 組裝頂層函式：`_mainFloorScreen(state)`、`_getFloorTile(state, btnIndex)`、`_getDoorButton(state, actButton)`、`_getVolumeButton(state, vType)`。這些函式只負責組裝 widget、把互動 callback（`onTap`／`onPointerDown`／`onPressed` 等）接到 `_MyHomePageState` 對應的方法上，本身不直接呼叫 `setState()`（原因見下方「畫面元件與狀態變更的分工」設計考量）。

以上 part 檔案中的頂層函式，凡是需要存取 `_MyHomePageState` 實例資料的，一律以明確參數 `state: _MyHomePageState` 傳入（非隱式閉包捕捉）。

**MyApp**（`lib/main.dart`）
App 進入點。`void main() { runApp(const MyApp()); }` ＋ `class MyApp extends StatelessWidget`。

### 業務邏輯與語音整合（`screens/home_page.dart`）

- **`stopAnimate()`**：新方法，內容是 `_animateController.stop(); _animateController.reset();`。從 `setElevatorDirection()` 裡抽出，讓「動畫該不該停」可以獨立於「`direction` 該不該變成 `idle`」被呼叫（見下方設計考量）。
- **`setElevatorDirection(Direction target)`**：`case Direction.idle` 分支改呼叫 `stopAnimate()`（原本直接寫 `_animateController.stop()`／`.reset()`，行為不變，純粹抽方法）。
- **`moveFloor(int moveIndex, void Function() goNextFloor)`**：到達目標樓層的分支裡，`setState()` 只窄地包住 `elevator.currentFloor` 的更新；接著（在 `setState()` 之外）依序呼叫 `_audioManager.request(fileName: 'sounds/ding.mp3', cb: stopAnimate)` 與 `_audioManager.request(fileName: floorMap[elevator.currentFloor]!.audioFile, cb: ...)`——樓層語音的 callback 裡才真正用 `setState()` 執行 `setElevatorDirection(Direction.idle)` 與 `floorMap[elevator.currentFloor]!.isTarget = false`，然後呼叫 `openDoor()`。
- **`openDoor()`**：guard 判斷通過後，`setState()` 把 `doorStatus` 改成 `opening`、`_animateController.repeat()`；接著呼叫 `_audioManager.request(fileName: actionMap[ActionType.open]!.audioFile)`（開門語音，跟開門動畫同時進行，不等語音播完）；`_timerManager.startTimer(TimerType.doorProc, ...)` 沿用原本邏輯，時間到才真正轉成 `open`。
- **`closeDoor()`**：一進入就先呼叫 `_audioManager.request(fileName: actionMap[ActionType.close]!.audioFile)`，再 `setState()` 把 `doorStatus` 改成 `closing`、開始動畫，其餘沿用原本邏輯。

### 按鈕音效與開關整合（`screens/home_page.dart`）

- **`floorTileOnTap(FloorButton myFloor, int btnIndex)`**：一進入就呼叫 `_sfxPlayer.request()`（不論後續業務邏輯是否真的觸發電梯移動，按下去都要有音效回饋），再執行原本樓層按鈕的業務邏輯（`isTarget` 切換、視情況觸發 `goUpFloor`/`goDownFloor`）。
- **`doorButtonOnTap(ActionButton actButton)`**：同樣先呼叫 `_sfxPlayer.request()`，再依 `actButton.btnType` 呼叫 `openDoor()`/`closeDoor()`；即使 `openDoor()`/`closeDoor()` 內部 guard 判斷後沒有實際動作，音效仍會播放。
- **`setDoorButtonPressed(ActionButton actButton, bool isPressed)`**：包住 `actButton.isPressed = isPressed` 的 `setState()`，供 `_getDoorButton` 的 `onPointerDown`/`onPointerUp`/`onPointerCancel` 呼叫。
- **`volumeButtonOnPressed(VolumeType vType)`**：依 `vType` 切換 `_sfxPlayer.isAllow` 或 `_audioManager.isAllow`，包在 `setState()` 裡觸發重繪。

## 二、設計考量與取捨

**三層架構：`models/` / `widgets/` / `screens/`（另加獨立的 `styles/`）**
`models/` 是純資料／邏輯物件；`widgets/` 是可重用的顯示元件（`StatelessWidget`，不含業務邏輯）；`screens/` 負責把 `widgets/` 組裝成完整畫面、並持有業務邏輯與可變狀態（`_MyHomePageState`）。`styles/` 特意獨立於 `models/` 之外，避免跟 Flutter 自己的 `Theme`/`ThemeData` 概念語意衝突。

**為什麼把「回傳 Widget 的方法」抽成獨立的 `StatelessWidget` class，而不是留在 `_MyHomePageState` 裡當方法**
獨立成 class 可以標記 `const`（減少不必要的重建）、在 DevTools 的 Widget Tree 中會是獨立節點方便除錯定位、建構子參數是明確的依賴注入，不像方法用閉包隱式讀取外層 state 欄位。

**抽取優先順序，依複雜度分級**
第一級：純粹「輸入→輸出」、不需要 callback（例：`ArrowIcon`）最先抽。第二級：需要透過建構子傳入 callback（例：`DoorButton`、`FloorTile`、`VolumeButton`）。第三級：需要共用 `AnimationController`／動畫狀態（例：`DirectionIcon`、`FloorDisplay`）最後處理，且需要額外設計「Controller 留在哪裡」。

**AppBar 曾經嘗試包成獨立的 `PortraitAppBar` widget，最後放棄**
`Scaffold.appBar` 要求 `PreferredSizeWidget` 介面，包成獨立 widget 需要多寫 `implements PreferredSizeWidget` ＋ `preferredSize` getter。評估這層額外成本換來的效益不高，最後決定不抽，直接在畫面組裝處寫 `AppBar(...)`。

**`DoorButton` 對外只用不帶參數的 `VoidCallback?`，不直接暴露 `Listener` 原生的 `PointerDownEvent` 等事件型別**
檢查過實際呼叫端，從未用到事件參數本身；暴露原始事件型別只是徒增外部依賴、沒有實際使用需求。內部用 lambda 把原生事件包一層再轉呼叫 `VoidCallback?`。

**`AnimationController` 為什麼留在 `_MyHomePageState`，只把算好的 `Animation<Offset>` 傳給 `DirectionIcon`**
`SlideTransition` 之類的動畫 widget 直接訂閱（listen）傳入的 `Animation` 物件本身即可局部重繪，不需要透過外層 `setState()`。顯示端只需要已經算好的 `Animation<Offset>`，不需要碰到原始 `Controller`；`Controller` 的啟動／停止仍由業務邏輯方法呼叫，留在 `_MyHomePageState`（詳見 `資料結構.md` 的 `AnimateOffset` 段落）。

**`DirectionIcon` 為什麼傳入整個 `Elevator` 物件，而不是只傳 `Direction`／`DoorStatus` 兩個欄位**
明知道傳整個物件耦合度較鬆，但考量呼叫端比較方便、不用逐一挑欄位，故意接受這個取捨。

**命名規則：避免 `models/` 跟 `widgets/` 撞名**
model 用領域概念命名（`FloorButton`、`ActionButton`），widget 用 UI／視覺角色命名，字彙盡量貼近 Flutter 自己既有 widget 的命名習慣（`Tile`、`Card`、`Chip`、`Bar`、`Panel`、`Icon`、`Button`、`View`）。例如資料是 `FloorButton`，畫面元件是 `FloorTile`；資料是 `ActionButton`，畫面元件是 `DoorButton`；純顯示用的圖示邏輯是 `ArrowIcon`。真的無法避免撞名時，退而求其次用 `import '...' as prefix;` 做區隔。

**橫式／直式版面為什麼用 `part`/`part of`，不是各自抽成獨立 `StatelessWidget`**
評估後兩個版面各自的組裝邏輯抽成 class 效益不高（不需要 `const` 優化、不會被其他畫面重用），但兩份程式碼混在同一個檔案中難以管理。Dart 的 private 存取權限以「檔案所屬 library」為界，`_MyHomePageState` 本身是私有 class，plain `import` 無法跨檔案存取，`extension`/`mixin` 也一樣受限；因此改用 `part`/`part of` 機制，讓多個實體檔案共用同一個 library 的私有存取權限。只有主檔案（`home_page.dart`）能宣告 `import`，part 檔案不能有自己的 import。

**檔案結構：`screens/home_page.dart` + `screens/home_page/portrait.dart` + `screens/home_page/landscape.dart` + `screens/home_page/shared.dart`**
曾考慮 `screens/home_page/main.dart` 的替代方案，但為避免跟真正的 App 進入點 `lib/main.dart` 混淆而放棄。`shared.dart` 用來存放直式／橫式都共用、且不需要呼叫 `setState()` 的 widget 組裝頂層函式（例如 `_mainFloorScreen`），避免同一份組裝邏輯在 `portrait.dart`／`landscape.dart` 各寫一份。

**畫面元件與狀態變更的分工：為什麼 `shared.dart`／`portrait.dart`／`landscape.dart` 裡的頂層函式不直接呼叫 `setState()`**
Flutter 的 `State.setState()` 被標記為 `@protected`——只能在該 `State` 自己的實例方法（或子類別）裡呼叫。在 class 外部呼叫，雖然因為 `part`/`part of` 給的存取權限技術上可行（能編譯、能執行），仍會被靜態分析器標記警告，違反框架原本「`setState()` 只給 `State` 自己用」的設計意圖。因此把「會呼叫 `setState()` 的邏輯」都留在 `_MyHomePageState` 自己的方法裡（`floorTileOnTap`、`doorButtonOnTap`、`setDoorButtonPressed`、`volumeButtonOnPressed`），`shared.dart`／`portrait.dart`／`landscape.dart` 裡的頂層函式只負責組裝 widget、把 callback 接到這些方法上，不直接碰 `setState()`。兩者職責分得更乾淨：頂層函式只管「畫面長什麼樣子」，`_MyHomePageState` 自己的方法管「狀態怎麼變」。

**`ActionButton.isPressed` 是否該改成 `StatefulWidget` 自己管理的 local state**
評估後這個 app 規模小，效能差異幾乎無感，但仍是值得養成的好習慣模式。決定延後處理，已列入 `學習路徑總覽.md` 中的後續學習計畫，此處不重複記錄理由。

**Race condition：語音播放期間點擊其他樓層按鈕，會繞過開關門流程直接觸發移動（Phase 11 發現並修正）**
`moveFloor` 到達目標樓層時，原本 `setElevatorDirection(Direction.idle)` 是立即同步執行的。Phase 11 把 `openDoor()` 延後到語音（`ding` + 樓層語音）播放完成後才觸發，導致「電梯已抵達（`direction == idle`），但語音還在播放、`doorStatus` 還沒真的變成 `opening`（仍是 `closed`）」這段空窗期出現——而這個狀態組合（`direction == idle && doorStatus == closed`），跟「電梯已經完整跑完一輪開關門、真正閒置」的狀態組合完全相同，導致樓層按鈕 `onTap` 的判斷式誤判，繞過開關門流程直接觸發 `goUpFloor()`/`goDownFloor()`。

修正前曾考慮兩個方向：(1) 新增一個獨立旗標專門標記「語音播報流程還沒跑完」；(2) 把 `setElevatorDirection(Direction.idle)` 延後到語音播放完成的 callback 裡才執行，讓 `direction` 跟 `doorStatus` 的轉變綁在同一個 `setState()` 裡、永遠同步變化，不會再出現中間態。最終選擇方向 (2)，理由是不想再引入一個語意上跟 `idle` 太接近、容易混淆的新欄位；曾嘗試過「借用 `floorMap[currentFloor].isTarget` 是否已被清除」當作替代判斷依據，但發現 `onTap` 一開始就會無條件 toggle 被點擊樓層的 `isTarget`，跟這個欄位本身「使用者想不想去這層樓」的語意耦合在一起，容易在邊界情況出包，因此放棄，改採方向 (2)。

**動畫停止時機為什麼要獨立成 `stopAnimate()`，不直接綁在 `direction` 變成 `idle` 的那一刻（Phase 11）**
上述修正的副作用：`direction` 現在要撐到語音全部播完才變成 `idle`，如果動畫的停止／重置也跟著綁在同一時間點，會讓使用者「已經聽到語音」但視覺上「方向箭頭動畫看起來還在移動」，聽覺跟視覺不同步、體感上有點怪。解法是把 `_animateController.stop()`／`.reset()` 抽成獨立的 `stopAnimate()` 方法，讓「動畫該不該停」這個純視覺層面的決定，可以跟「`direction` 該不該變成 `idle`」這個業務邏輯層面的決定分開判斷——`stopAnimate()` 改成在 `ding` 音效播放完成的當下就呼叫（比樓層語音、`direction` 轉變都早），讓動畫更早停下來，聽覺與視覺的同步感更好。這個 callback 不需要包 `setState()`，因為 `AnimationController` 的變化是被動畫 widget 直接訂閱（listen）的，跟 `AnimateOffset` 原本的設計理由一致（詳見 `資料結構.md`）；但另一個會動到 `direction`／`isTarget` 的 callback，因為是普通欄位，仍然需要包 `setState()` 才能通知 Flutter 重繪。
