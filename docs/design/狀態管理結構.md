# 狀態管理結構

本文件涵蓋 `providers/` 這一層——透過 Riverpod 管理的跨畫面共用狀態，與 `資料結構.md`（`models/` + `styles/`，純資料/邏輯層，刻意不依賴 Flutter/Riverpod）、`元件結構.md`（`widgets/`）、`畫面結構.md`（`screens/`）互補（Phase 16 新增，`providers/` 獨立於既有三層之外，因為它的角色是「畫面與共用狀態之間的接線」，不是任何一層的延伸，詳見下方設計考量）。格式比照其餘三份文件，分兩個區域：

- **一、狀態速查**：開發中需要立即查詢的資訊——欄位、方法、用途。只看目前的正確狀態，不含歷史沿革。
- **二、設計考量與取捨**：需要判斷「為什麼這樣設計」時才需要查閱。

---

## 一、狀態速查

### VolumeState（`providers/volume.dart`）

音效／語音開關狀態的資料形狀，不可變（immutable）。

- `isAllowSfx: bool`（final）— 是否允許播放按鈕提示音效
- `isAllowVoice: bool`（final）— 是否允許播放語音播報
- `copyWith({bool? isAllowSfx, bool? isAllowVoice})` — 產生一份只變更指定欄位、其餘欄位照抄的新 `VolumeState`

### VolumeNotifier（`providers/volume.dart`）

`extends Notifier<VolumeState>`，持有並變更 `VolumeState`。

- `build()` — 回傳初始狀態：`VolumeState(isAllowSfx: true, isAllowVoice: true)`
- `toggleSfx()` — `state = state.copyWith(isAllowSfx: !state.isAllowSfx)`
- `toggleVoice()` — `state = state.copyWith(isAllowVoice: !state.isAllowVoice)`

### volumeProvider（`providers/volume.dart`）

`final volumeProvider = NotifierProvider<VolumeNotifier, VolumeState>(VolumeNotifier.new);`——串接 `VolumeNotifier`／`VolumeState` 的頂層宣告，`ProviderScope`（`main.dart`，包住整個 App）底下任何地方都能透過這個變數存取。

**目前的使用者**：

- `HomePage`（`ConsumerWidget`）：`ref.watch(volumeProvider)` 讀取顯示用的 `isAllowSfx`／`isAllowVoice`；按鈕 `onPressed` 用 `ref.read(volumeProvider.notifier).toggleSfx()`／`toggleVoice()`
- `PanelPage`（`ConsumerStatefulWidget`／`ConsumerState`）：`requestVoicePlayer()`／`requestSfxPlayer()` 內用 `ref.read(volumeProvider)` 讀取當下值，轉傳給 `VoicePlayer.request()`／`SfxPlayer.request()` 的 `isAllow` 參數（詳見 `畫面結構.md`）

## 二、設計考量與取捨

**為什麼 `providers/` 是獨立的第四層，不是 `models/` 的一部分**
`models/` 目前所有東西（`Elevator`、`TimerManager`、`VoicePlayer`、`SfxPlayer`、`FloorButton`……）都是「獨立自足」的類別——可以在任何情境下直接 `new` 一個出來就能用，不需要透過任何額外機制去「取得」它。`VolumeNotifier` 不一樣，它必須繼承 Riverpod 框架的 `Notifier<T>`，而且幾乎不可能被單獨 `new` 出來使用——它整個存在的意義，就是被登記進 `NotifierProvider` 這個宣告裡，透過 `ProviderScope`／`ref` 機制去讀取。角色比較像「畫面與共用狀態之間的接線」，不像 `models/` 裡的東西代表某個業務概念本身，因此獨立成 `providers/`，避免混進 `models/` 一直保持的「不管用哪種狀態管理方案，這些類別都能原封不動繼續用」的原則。

**資料夾／檔案命名為什麼是複數 `providers/`、檔案是單數 `volume.dart`**
比照 `models/`／`widgets/`／`screens/`／`styles/` 都是複數的既有慣例；檔案內容目前只有音效／語音這一組狀態，直接以主題命名 `volume.dart`，之後如果新增其他跨畫面共用狀態（例如動物模式相關），可以視情況新增檔案或評估是否需要再拆分。

**為什麼 `VolumeState` 的欄位是 `final`、要透過 `copyWith()` 產生新物件，而不是原地修改**
Riverpod 的 `Notifier.state` 是一個特殊的 setter，賦值給它才會觸發通知、讓訂閱者（`ref.watch(...)` 的畫面）重建；原地修改物件內部欄位不會經過這個賦值動作，訂閱者永遠不會知道狀態變了。就算欄位真的能被直接改，同一個物件參照也可能被 Riverpod 預設的 `==` 比較判定成「沒有變化」而跳過重建。用 `copyWith()` 每次產生全新物件，才能確保變化能被正確偵測到。

**為什麼 `SfxPlayer`／`VoicePlayer` 的 `request()` 改成接受 `bool isAllow` 參數，而不是直接接受 `WidgetRef` 自己讀狀態**
讓這兩個 class 直接依賴 `WidgetRef` 會強迫它們 `import` Riverpod、綁死套件版本，還會讓它們拿到「能讀寫整個 App 共用狀態」的權限，而不是只拿到真正需要的那一個布林值；也會讓單元測試多一層不必要的 Riverpod 環境設置成本。改成接受單純的 `bool`，`SfxPlayer`／`VoicePlayer` 完全不需要知道 Riverpod 存在，判斷邏輯（能不能播放、callback 是否照樣執行）維持在這兩個 class 內部，呼叫端（`_PanelPageState` 的 `requestVoicePlayer()`／`requestSfxPlayer()`）只負責提供當下的值。詳見 `資料結構.md` 的 `VoicePlayer`／`SfxPlayer` 段落。

**`_getVolumeButton`（`HomePage`）／`requestVoicePlayer`／`requestSfxPlayer`（`PanelPage`）裡，為什麼切換動作用 `ref.read()`、顯示用的值用 `ref.watch()`**
`ref.watch()` 是「宣告畫面渲染依賴」，只該在 `build()` 執行過程中呼叫，狀態變了會觸發重建；`onPressed` 這類事件處理不是 `build()` 的一部分，只是一次性動作，此時該用 `ref.read()`——不訂閱、不重建，用完即丟。`HomePage` 顯示開關圖示需要即時反映狀態 → `watch`；切換開關、`PanelPage` 判斷當下能不能發聲，都是一次性讀取或指令 → `read`。

**`ConsumerState`（`PanelPage`）與 `ConsumerWidget`（`HomePage`）的 `ref` 取得方式為什麼不一樣**
`ConsumerState<T>` 其實是繼承 `State<T>`，`ref` 是內建在 class 裡的屬性（跟 `context`、`widget` 一樣），`build()` 簽名維持 `Widget build(BuildContext context)`，不需要多加參數。`ConsumerWidget` 沒有獨立的 `State` 物件可以掛屬性，`ref` 是以參數形式傳入：`Widget build(BuildContext context, WidgetRef ref)`。兩者容易混淆，開發時曾把 `ConsumerState` 的 `build()` 誤寫成兩參數版本，導致 `invalid_override` 編譯錯誤。
