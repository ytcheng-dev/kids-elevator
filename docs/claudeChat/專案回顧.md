# 專案回顧：Kid's Elevator（電梯面板模擬 App）

> 括號內是出處：「Phase N」指 `PhaseN_學習紀錄.md`，其他則寫出文件名稱。

## 一、這個專案做了什麼

**Kid's Elevator** 是一個給幼兒玩的電梯面板模擬 App，只做 Android。它有兩個模式：

- **面板模式**：7 個樓層、開關門、語音播報與音效
- **動物模式**：語音出題，答對或答錯時播放用 Google Flow 生成的動物動畫

專案的目的是從零學習 Flutter／Dart，不是快速做出產品。2026-08-14 開始，2026-09-27 收尾並打上 `v1.0.0`，前後約 6 週半：前段是週一到五每天 1～2 小時，約 9/18 起改為每天 6～8 小時。

整個過程分成 26 個 Phase：Phase 0～18 是功能開發，19～26 是測試系列，另外還有一條 Android SDK 工具鏈更新的支線。收尾時有 70 個測試、`flutter analyze` 無警告、行覆蓋率 66.1%。

## 二、學到了什麼

### 1. Dart／Flutter 基礎

**樣式是綁在特定元件上的，不能像 CSS 一樣全部寫在同一個 tag**
- `Container` 的 `color` 和 `decoration` 不能同時用；邊框顏色要寫在 `BorderSide` 裡，沒有獨立的 `borderColor`（Phase 6）
- 文字置中要設 `Text` 自己的 `textAlign`，外面包的 `Expanded` 管不到（Phase 3）
- 沒有 CSS class 可以用，共用樣式要自己抽成 `static` 常數和函式（`CSSManager`）（Phase 6）

**要考慮型別**
- JS 的參數在宣告、使用、甚至替換時都不需要考慮型別，Dart 需要
- 樓層資料一開始考慮過 `Map<String, dynamic>`（類似 JS 物件），最後選了自訂 class，因為型別明確、IDE 能自動完成（Phase 4）

**null 的處理比 JS 嚴格很多**
- 型別預設不能是 null，要允許 null 得明確加 `?`（Phase 1）
- 具名參數如果型別不能是 null，就要加 `required`；這些檢查在編譯時就會擋下來（Phase 1）
- `Map` 用 `[]` 取值會回傳可能是 null 的型別，確定 key 存在時要加 `!` 斷言（Phase 4）

**`const`／`final`／`var` 要區分**
- JS 用 `const`、`let` 就能處理幾乎所有事情，而且什麼時候都能用；Dart 要分清楚
- `const` 在編譯時就要確定值，`final` 在執行時第一次賦值後就不能再改（Phase 1）
- `Theme.of(context)` 在執行時才拿得到，所以不能放在 `const` 裡（Phase 2）
- 外層寫了 `const Row`，裡面的 `Container` 沒有 `const` 建構子，就會報錯（Phase 3）

**Flutter 每次都重新描述整個畫面，DOM 是找到節點直接改**
- DOM 是抓到某個節點直接改它，Flutter 是每次重新描述「畫面現在應該長怎樣」，交給框架去畫（Phase 2）
- 小觀察：畫面結構跟 HTML 一樣一層包一層，誰在誰裡面，看程式碼怎麼包就知道

**Stateless／Stateful 是新概念**
- 在 JS 裡，資料改了之後通常不用自己去通知畫面重畫
- Widget 每次重建都會整個丟掉重做，所以會變的資料要放在存活比較久的 `State` 物件裡（Phase 2、4）
- `setState` 不知道你改了什麼，只知道「要重畫」，所以修改資料的程式碼要寫在它的 callback 裡面（Phase 4）

**`() => {}` 的陷阱**
- 在 JS 裡，`() => { ... }` 的 `{}` 是函式本體；在 Dart 裡，`=>` 後面只能接一個表達式，`{}` 會被當成 Set（集合）
- 例如 `onTap: () => {print(btnText)}`，實際上是「每次點擊時建立一個 Set，裡面放 `print(btnText)` 的結果」。建立 Set 時會先執行 `print`，所以畫面上看起來完全正常，`flutter analyze` 也不會報錯，很難發現寫錯了（Phase 4）
- 正確寫法：只做一件事用 `() => print(btnText)`，要做多件事用 `() { ...; ...; }`

### 2. 版面與響應式

**`Expanded`：分配剩餘空間**
- Flutter 沒有 `width: 10%` 這種百分比寫法。`Expanded` 會依 `flex` 比例分配 `Row`／`Column` 的剩餘空間，概念類似 CSS 的 `flex-grow`（Phase 3）
- 它只能直接放在 `Row`／`Column` 底下，而且只影響所在的那個軸（Phase 3）
- 踩過的坑：
  - 7 個按鈕全部包上 `Expanded` 後，`spaceEvenly` 就沒有作用了，因為剩餘空間已經被分完（Phase 3）
  - 內層 `Column` 沒有被 `Expanded` 撐開時，高度只有子元件疊起來那麼高，`spaceAround` 沒有空間可以分配（Phase 3）

**版面比例的計算**
- Phase 6 只用螢幕寬度的百分比來推算按鈕大小，遇到某些螢幕比例就會 overflow。當時先用 1.5 比例的長方形暫代，並新增 Phase 7 專門處理響應式
- Phase 7 的做法：分別用寬度和高度推算正方形的邊長，取比較小的那個，這樣兩個方向都不會 overflow
- 百分比常數最後命名為 `shortSidePercent`／`longSidePercent`，代表「按鈕在短邊／長邊各佔多少百分比」。不管直式或橫式，短邊都排 2 個按鈕、長邊都排 5 個，所以同一組常數可以套用在兩種版面。原本的名字 `buttonWidthPercent`／`buttonHeightPercent` 在橫式版面裡意思剛好相反，容易看錯（Phase 7）
- 文字和圖示改用 `FittedBox` + `BoxFit.contain`，跟著按鈕大小縮放，不用寫死 `fontSize`（Phase 7）

**`LayoutBuilder`：讀取實際分配到的空間**
- `constraints` 是父層真正允許這個位置的大小，已經扣掉 padding、其他兄弟元件和 AppBar（Phase 7）
- 踩過的坑：`Row` 裡沒有包 `Expanded` 的子元件，讀到的 `maxWidth` 是還沒扣掉 `Expanded` 兄弟之前的寬度，會比實際畫出來的大很多（Phase 7）

**`MediaQuery`：整個裝置的資訊**
- `size` 是整個螢幕的尺寸，包含 AppBar 的高度。橫式版面一開始用它來算高度百分比，數字就不對，後來改用 `LayoutBuilder`（Phase 7）
- 用 `orientation` 判斷直式或橫式，兩種方向各自組一套版面。這個 App 只有單一全螢幕畫面，所以不需要用 `OrientationBuilder`（Phase 7）
- 只能在拿得到 `BuildContext` 的地方使用，像 `CSSManager` 這種獨立的 class 就拿不到（Phase 6）

### 3. 動畫

寫 JS／HTML 時幾乎沒有碰過動畫，整個領域都是新的概念。

**Controller 只管時間軸，動畫內容要靠其他元件來表現**
- `AnimationController` 只負責時間軸：什麼時候開始、停止、重複（`.repeat()`／`.stop()`／`.reset()`），它提供的只是 0.0～1.0 的進度值（Phase 8）
- `Tween` 負責把 0.0～1.0 的進度換算成實際要用的數值，例如位移的起點和終點（`Offset`）（Phase 8）
- `SlideTransition` 這類元件才是真正把數值畫到畫面上的角色（Phase 8）
- 因為 Controller 跟畫面上的元件是分開的，同一個 Controller 可以搭配多組 `Tween`：開門、關門、上樓、下樓共用一個 Controller，畫面依照目前狀態決定要接哪一組（Phase 8）

**隱式動畫和顯式動畫**
- `AnimatedContainer` 這類隱式動畫：屬性值改變時自動補間一次，跑完就結束（Phase 8）
- `AnimationController` 這類顯式動畫：自己控制時間軸。開門中、關門中需要「一直重複，直到狀態改變才停」，這是隱式動畫做不到的，所以選用 Controller（Phase 8）

**其他細節**
- Controller 需要 `vsync`，所以 `State` 要加上 `with SingleTickerProviderStateMixin`；Controller 要在 `initState()` 才能建立，欄位宣告時要用 `late`（Phase 8）
- `SlideTransition` 的位移不會自動被裁切，動畫會跑出黑色顯示框，要在外層 `Container` 加上 `clipBehavior`（Phase 8）

### 4. 元件化與專案結構

基本上是一個 refactor 的過程（Phase 9 的原則就是「純重構、行為不變」），只是以前寫 JS 不會分得這麼細，這裡要明確分類。

**明確分類：`models/`、`screens/`、`widgets/`**
- 原本全部寫在一個 `main.dart` 裡，拆成四類（Phase 9）：
  - `models/`：資料與邏輯（`Elevator`、`TimerManager`、enum 等）
  - `styles/`：樣式常數（`CSSManager`）
  - `widgets/`：可重用的顯示元件（`FloorTile`、`DoorButton` 等）
  - `screens/`：頁面，負責組裝元件和處理業務邏輯
- 最後大約拆成 15 個檔案（Phase 9）

**拆成 widget class 和用 function 產生 widget 的差異**
- 獨立的 `StatelessWidget` class 可以標 `const`，讓 Flutter 略過不必要的重建（Phase 9）
- 在 DevTools 的 Widget 樹上是獨立節點，除錯時比較好找（Phase 9）
- 需要的資料都從建構子傳入，依賴關係很清楚；function 則是直接讀外層 State 的欄位，看不出它依賴了什麼（Phase 9）
- 抽出的順序依複雜度：先抽純輸入輸出的，再抽需要 callback 的，最後才處理需要共用動畫的（Phase 9）

**命名的基本規則**
- model 已經用了 `FloorButton`，widget 也想用同一個名字，最後只能改成 `FloorTile`（Phase 9）
- 整理出來的規則：model 用領域概念命名，widget 用 UI 角色命名，盡量貼近 Flutter 既有的用詞（`Tile`、`Card`、`Bar`、`Icon`、`Button` 等）；真的撞名時才用 `import ... as` 區分（Phase 9）

**拆檔案時遇到的私有存取限制**
- Dart 的 `_` 私有範圍是以檔案為界，拆出去的檔案就存取不到 `_MyHomePageState`。直式和橫式版面最後用 `part`／`part of` 拆開，讓它們屬於同一個 library、共用私有存取權限（Phase 9）

### 5. 多頁面導覽

**`Navigator` 的使用**
- `Navigator` 管理一個畫面堆疊：`push` 放入新畫面，`pop` 回到上一個。概念類似 JS 單頁應用用 `history.pushState()` 切換畫面，只是這個堆疊是 App 自己管的（Phase 14）
- `MaterialPageRoute` 是畫面的容器，負責切換動畫和返回鍵的處理，本身不是畫面（Phase 14）
- 每次 `push` 都會建立全新的畫面和 `State`，所以重新進入面板模式時一定是初始狀態。評估後決定不保留上次的狀態（Phase 14）
- 畫面變成可以被 `pop` 之後，`AppBar` 會自動多出一個返回箭頭，跟自己做的「回主選單」按鈕重複，要用 `automaticallyImplyLeading: false` 關掉（Phase 14）

**`Dialog` 會被 `pop` 掉，所以動物動畫改用 `Stack`**
- `showDialog` 本質上是在 `Navigator` 裡推入一層路由。`barrierDismissible: false` 只能擋住「點視窗外面關閉」，擋不住 Android 的系統返回鍵（Phase 17）
- 動物動畫播放時不能被中途關掉，所以改用 `Stack` + `Positioned.fill`，在同一個畫面裡疊一層，完全不經過 `Navigator`（Phase 17）

### 6. 資源

使用方式跟 JS 感覺差不太多，比較麻煩的是設定。

**每個資源資料夾都要寫進 `pubspec.yaml`**
- 資料夾路徑結尾加斜線（`assets/sounds/`）可以涵蓋底下所有檔案，但不會自動抓子資料夾，每一層都要各自宣告（Phase 11）
- 修改後要重新執行 `flutter pub get`（Phase 11）
- 宣告的檔案會在 build 時打包進 APK，執行時讀到的是唯讀資源，不是檔案系統上的路徑（Phase 11）

**不同套件的路徑慣例不一樣**
- `Image.asset()` 要寫完整路徑（`assets/images/...`），`audioplayers` 的 `AssetSource` 則不能加 `assets/` 前綴，因為套件會自動補上。一開始照完整路徑寫，結果找不到檔案（Phase 11）

### 7. 狀態管理

**Widget 的 state：狀態要放在哪一層**
- 主選單一開始用 `StatelessWidget` 就夠了。討論後發現，要不要改成 `StatefulWidget`，取決於「音效開關這份狀態放在哪裡管」，而不是畫面上有沒有會變的東西（Phase 14）
- `HomePage` 和 `PanelPage` 是透過 `Navigator` 推入的兩個平行畫面，不是父子關係，沒辦法用建構子把狀態一路傳下去，所以需要跨畫面共用的機制（Phase 16）

**`setState` 的使用**
- 一般的 Dart 欄位（例如 `elevator.direction`）改變時，Flutter 不會自動發現，要呼叫 `setState` 才會重畫（Phase 11）
- 動畫不一樣：`SlideTransition` 會直接監聽 `Animation` 物件，自己局部重畫，不需要 `setState`。同一個非同步 callback 裡，這兩種欄位的處理方式不同（Phase 9、11）

**Provider／Notifier 的使用（Riverpod）**
- 選 Riverpod 而不是 Provider：查證當時 Riverpod 的下載量和維護活躍度已經超過 Provider，而且不依賴 `BuildContext` 的位置，測試時也比較容易替換成假的實作（Phase 16）
- 三個組成：`ProviderScope` 包在整個 App 最外層；provider 宣告成頂層變數；`Notifier` 負責持有和修改狀態（Phase 16）
- `state = state.copyWith(...)` 這個重新賦值的動作才會觸發通知，直接修改欄位不會（Phase 16）
- `ref.watch` 用在 `build()` 裡，狀態改變時會重畫；`ref.read` 用在按鈕事件這類一次性的動作，只讀當下的值（Phase 16）
- 要使用 provider 的畫面，要換成 Riverpod 版本的 widget（Phase 16）：
  - `StatelessWidget` → `ConsumerWidget`（`HomePage`）
  - `StatefulWidget` + `State` → `ConsumerStatefulWidget` + `ConsumerState`（`PanelPage`）
- 兩者取得 `ref` 的方式不同：`ConsumerWidget` 沒有 `State` 可以放屬性，所以 `ref` 是 `build()` 的第二個參數；`ConsumerState` 的 `ref` 是屬性（跟 `context`、`widget` 一樣），`build()` 只有一個參數。一開始把兩者搞混，出現 `invalid_override` 錯誤（Phase 16）
- 播放器的 `request()` 只接收一個 `bool isAllow`，不直接接收 `ref`，讓 `models/` 不依賴 Riverpod（Phase 16）

### 8. 非同步與音訊

**`VoicePlayer` 和 `SfxPlayer` 搶佔音訊焦點**
- 兩個播放器的策略刻意設計成不同：`VoicePlayer` 是排隊依序播報，`SfxPlayer` 是「正在播就丟棄新的請求」（Phase 12）
- 實測時發現：到站播 `ding` 的時候按下按鈕，`SfxPlayer` 會搶走音訊焦點，`ding` 被系統中斷，播放完成的事件沒有觸發，後面的樓層語音就不播了，方向箭頭的動畫也停不下來（Phase 12）
- 音訊焦點是 Android 協調「誰可以播聲音」的機制，不是能不能發出聲音的技術限制（Phase 12）
- 一開始試了 `PlayerMode.lowLatency`，但這個模式不會觸發播放完成事件，`SfxPlayer` 會一直以為自己在播放，之後的請求都被丟掉。最後改回預設模式，用 `AudioContextConfigFocus.mixWithOthers` 讓 `SfxPlayer` 不申請焦點（Phase 12）

**播放完成的監聽和 callback**
- 「到站 → 語音播完 → 才開門」這類流程，靠監聽播放完成事件（`onPlayerComplete`）再執行 callback 串起來（Phase 11）
- 呼叫 `.play()` 之後，播放器的 `state` 不會馬上更新。連續送出兩個播放請求時，第二個會讀到舊的狀態，以為沒有東西在播，直接搶播。改成自己維護一個同步更新的 `isPlaying` 旗標（Phase 11）
- 播放完成時，要先執行剛播完那個音檔的 callback，再播下一個。順序反了的話，callback 已經被換成下一個音檔的（Phase 11）
- 關閉語音時，callback 還是要執行，只是不發出聲音。因為 callback 裡綁著開門這類業務邏輯，不執行電梯就會卡住（Phase 12）
- 影片播放器（`video_player`）沒有現成的播放完成事件，用 `addListener()` 自己比對 `position >= duration` 來判斷（Phase 17）

### 9. 測試

這個專案之前完全沒有寫過自動化測試，整個測試系列（Phase 19～26）都是從零開始。

**區分 `test` 和 `testWidgets`**
- `test` 用在純 Dart 的邏輯，例如 `Elevator`、`TimerManager`，沒有畫面，跑得最快（Phase 19）
- `testWidgets` 在 Dart VM 裡模擬一個 Flutter 環境，有 widget 樹、版面配置、手勢系統，但沒有真正的螢幕，不需要實機（Phase 20）
- 能不能用 `test` 取決於程式碼結構：`floorTileOnTap` 綁在 `State` 上、會呼叫 `setState`，就只能用 `testWidgets` 測（Phase 19）

**用 `pump` 推進畫面**
- 流程是 `pumpWidget` 掛上畫面 → `find` 找目標 → `tap` 操作 → `pump` 讓畫面前進 → `expect` 驗證（Phase 20）
- `setState` 只是標記「需要重畫」，測試環境不會自己畫下一個 frame，所以點擊之後要 `pump`（Phase 20）
- `tap` 會一次完成按下和放開。要停在按下的那一刻，改用 `startGesture`，再用 `up()`／`cancel()` 結束（Phase 20）

**Finder 的使用**
- `find.byKey`、`find.byType`、`find.descendant` 等等；畫面上有 7 個 `FloorTile`，要靠 `Key` 才能指定其中一個（Phase 19、20）
- Finder 只是查詢條件，可以重複使用；`tester.widget()` 拿到的是當下的快照，每次 `pump` 之後都要重新取（Phase 20）
- 踩過的坑：`const ValueKey floorTile1 = ValueKey('floorTile1')` 找不到 widget。因為沒寫泛型的 `ValueKey` 是 `ValueKey<dynamic>`，跟畫面上的 `ValueKey<String>` 型別不同，比對結果不相等（Phase 22）

**`FakeVoicePlayer`（依賴注入）**
- `SfxPlayer` 的建構子一執行就會碰到 `audioplayers`，所以測試時要換掉整個播放器（Phase 22）
- 不能用 `extends`：子類別一定會執行父類別的建構子，而且私有方法跨檔案也無法覆寫。改用 `abstract class` + `implements`，建立 `SfxPlayerBase`／`VoicePlayerBase` 介面，`PanelPage` 從建構子接收播放器（Phase 22）
- `FakeVoicePlayer` 改了三版：第一版同步呼叫 callback，跟真的播放器行為不一致；第二版改用 `Timer` 延遲觸發；第三版補上排隊機制，對應「`ding` 接著樓層語音」連續兩個請求的情況（Phase 22）

**`FakeVolumeNotifier`**
- 用 `ProviderScope(overrides: [volumeProvider.overrideWith(...)])` 把真正的 `VolumeNotifier` 換成 `FakeVolumeNotifier`，讓畫面一開始就處於指定的開關狀態（Phase 21）
- `FakeVolumeNotifier` 繼承 `VolumeNotifier`，只覆寫 `build()` 的初始值，切換開關的方法還是用真正的實作（Phase 21）
- 原本打算用 `PanelPage` 練習 override，但 `PanelPage` 的 `build()` 不讀 provider，override 寫對寫錯畫面都一樣，測試不可能失敗。所以改用 `build()` 裡有 `ref.watch` 的 `HomePage` 來練習，並把 `overrides` 那一行拿掉，確認測試真的會變紅（Phase 21）
- 沒有包 `ProviderScope` 時，pump 還是會通過；要等到點擊觸發 `ref.read` 那一刻才會出錯，因為 provider 是在第一次讀取時才需要容器（Phase 21）

**mock channel：追蹤原始碼，理解 Dart 端和原生端的差別**
- 一開始的測試出現「假綠燈」：錯誤發生在測試結束之後，因為建構子裡的非同步工作沒有被 `await`（Dart 的建構子不能 `async`）（Phase 25）
- Dart 端和原生端（Android 的 Kotlin）透過 channel 溝通：`MethodChannel` 是 Dart 呼叫原生端，`EventChannel` 是原生端主動推送事件給 Dart。類比 HTTP：channel 名稱像 base URL，method 像 endpoint（Phase 25）
- 從錯誤訊息找到 channel 名稱，再用 `pubspec.lock` 確認版本，到 pub cache 裡追 `audioplayers` 的原始碼，一路追出建構和播放時會送出哪些訊息（Phase 25）
- 用 `setMockMethodCallHandler` 攔截 `MethodChannel`、`setMockStreamHandler` 模擬 `EventChannel`，最後整理成 `MockAudioPlayersPlatform`（Phase 25）
- 時機很重要：prepared 事件要在收到 `setSourceUrl` 時才推送，太早推送的話，當下沒人在聽，事件就消失了（Phase 25）

**判斷每個測試要做多深**
- 圖示切換（音效／語音 × 開／關，四種圖示）歸 `VolumeButton` 自己的測試，`HomePage` 只測「provider 的值有沒有接到按鈕的 `isAllow`」（Phase 21）
- `PanelPage` 的測試不需要管 `VoicePlayer` 有沒有正常播放，只要確認觸發成功或失敗之後，`PanelPage` 自己的反應是否正確，所以用假的播放器就好（Phase 22）
- `SfxPlayer` 的 mock channel 測試也只驗證 `SfxPlayer` 自己的責任（`audioFocus`、檔案路徑、`resume` 次數），不驗證 `init`、`create` 這些 `audioplayers` 內部送出的訊息，否則就是在替套件的內部實作把關（Phase 25）
- 分工的判斷：測試對象跟原生端無關、只是間接碰到 → 用依賴注入換掉；測試對象本身就是直接跟原生端溝通的最後一層 → 在 channel 攔截（Phase 25）

**`fakeAsync` 和 `pump` 的比較**
- `fakeAsync` 換掉的是「保管計時器的人和時鐘」：`Timer` 建立時會問目前的 zone，在 `fakeAsync` 裡面建立的計時器就會進入假的清單（Phase 26）
- 假時鐘只有在呼叫 `elapse` 時才會前進。在 `fakeAsync` 裡用 `await` 等時間，後面的程式碼永遠不會執行，而且測試常常不會報錯，看起來像是通過（Phase 26）
- `pump(Duration)` = `elapse` + 畫一個 frame。`testWidgets` 本身就跑在 `fakeAsync` 裡，所以有畫面時用 `pump`；`test()` 沒有畫面，只需要推進時間，用 `elapse` 就夠（Phase 26）
- `timer_manager_test.dart` 從約 16 秒縮短到不到 1 秒，精確度從前後 1 秒提升到 1 毫秒（Phase 26）
- `DateTime.now()` 不經過 zone，`fakeAsync` 控制不了，要改用 `clock.now()`（Phase 26）

### 10. Android 建置與發布

**`flutter upgrade` 引發的支線任務**
- Phase 10 加入 `audioplayers` 時，套件要求 `compileSdk 35`，專案當時是 34。這是 Android 自己的建置工具 Gradle 的限制，`pubspec.yaml` 管不到（Phase 10）
- 比較兩種修法：把 `compileSdk` 直接寫死成 35，或是 `flutter upgrade` 讓 Flutter 自動管理的版本跟著更新。`flutter upgrade` 影響的是整台電腦的 Flutter SDK（3.24.4 → 3.47.2），類似升級 Node.js 本身（Phase 10）
- 升級後，新版 Flutter 對 Android 建置工具的最低版本要求變高，連帶要更新 Android SDK（`android-36`、`build-tools 28.0.3`）、Gradle（8.3 → 8.14）、AGP（8.1.0 → 8.11.1）、Kotlin（1.8.22 → 2.2.20），另開一條支線處理（`支線_AndroidSDK工具鏈更新_學習紀錄.md`）
- 升級 Gradle 時遇到「雞生蛋」問題：官方的升級指令要先用舊版 Gradle 跑起來，但一跑就被新版 Flutter 的版本檢查擋下。最後直接編輯 `gradle-wrapper.properties` 裡的版本號（`支線_AndroidSDK工具鏈更新_學習紀錄.md`）
- 這三個版本目前都還有「即將不支援」的警告，留到下一個專案處理（`專案收尾清單.md`）

**App 圖示的設定**
- 用 `flutter_launcher_icons` 從一張圖片產生各種解析度的 Android 圖示，並設定 adaptive icon：背景色 + 前景圖（`app/pubspec.yaml`）
- 圖示本身不要自己畫邊框，交給背景色處理。不同手機的顯示規則不同，自己畫的邊框可能被切成奇怪的形狀
- 前景圖要預留邊界（`adaptive_icon_foreground_inset: 18`），因為不同的顯示規則會把圖示裁成不同的形狀和範圍

**App 識別碼的概念**
- `applicationId` 是 App 在裝置上的唯一身分。原本是 `flutter create` 預設的 `com.example.elevator`，收尾時改成 `com.ytc.kidselevator`，`namespace` 和 `MainActivity.kt` 的 package 路徑也一起調整（`專案收尾清單.md`）
- 識別碼不同，系統就當成另一個 App，所以要先移除舊的 `elevator`，再安裝新的 release 版（`專案收尾清單.md`）
- 桌面顯示的名稱是另一個設定：`AndroidManifest.xml` 的 `android:label` 從 `elevator` 改成 `Kid's Elevator`（`專案收尾清單.md`）

## 三、哪些可以做得更好

### 1. 沒有先規劃全域的樣式

最早只為 `PanelPage` 做了 `CSSManager`，而且是用到什麼才定義什麼，沒有先規劃整個 App 的樣式。
- 到 9/16 體質檢視時，顏色來源有三套同時存在：`CSSManager`（面板模式）、`LayoutCss`（主選單和部分動物模式），以及動物模式直接寫死在元件裡的色碼，數值接近但不完全一樣（`專案體質檢視報告.md`）
- `MaterialApp` 的 `ThemeData` 從 `flutter create` 之後就沒有使用過。Phase 6 已經知道 `Theme`／`ThemeData` 是 Flutter 對應全域樣式的機制，但當時沒有採用（Phase 6、`專案體質檢視報告.md`）
- 最後收斂成 `LayoutCss`（四組色階 + 文字大小 + 間距）作為唯一來源

**如果重來**：開始做畫面之前，先定好色票、文字大小、間距這些全域樣式，畫面只引用，不自己定義顏色。

### 2. 沒有預先考慮測試

當時沒有要寫測試的概念，所以相關的準備工作都沒有先做。前 18 個 Phase 完全沒有測試，等到 Phase 19 才開始寫，才發現：
- 業務邏輯寫在 `State` 的方法裡、直接呼叫 `setState`，只能用 widget 測試驗證（Phase 19）
- `SfxPlayer`／`VoicePlayer` 在 `initState` 裡直接建立，建構子一執行就碰到原生端，只好回頭補上介面和依賴注入（Phase 22）
- `SfxPlayer` 的判斷邏輯和非同步的檔案讀寫綁在一起，而且不回報結果，測試只能用固定時間等待（Phase 25）
- 長按開門用 `DateTime.now()` 計時，`fakeAsync` 控制不了，這段到收尾都還沒有測試（Phase 26）

**如果重來**：每新增一個 model 或 widget，就同時把對應的測試寫出來。設計上，會碰到外部資源（音訊、原生端）的類別先定義介面、從建構子注入；能抽成純 Dart 的判斷邏輯放在 model，不綁在 `State` 上。

### 3. 設計文件沒有及時同步

邊做邊設計的過程中，資料結構會不斷改變，文件跟程式碼脫節是難免的。但這個專案的設計文件也是每個 Phase 開場時給 Claude 的背景資料，文件過時，Claude 就會根據錯的資訊引導。
- Phase 9～16 大多在 Phase 結束時就同步了文件
- 脫節主要發生在 Phase 17、18 延後整理的期間：9/16 體質檢視時，發現三份結構文件都沒有反映動物模式，`畫面結構.md` 對 `dispose()` 的描述也已經過時（`專案體質檢視報告.md`）
- Phase 22～26 改了程式碼，收尾時又要逐份對照程式碼同步一次（`專案收尾清單.md` B-2）

**如果重來**：每個 Phase 結束時就同步文件，不要累積到之後一起整理。

## 四、學習方式的回顧

### 有效的做法

- **一個對話只處理一個 Phase**：避免失焦。結束時產出學習紀錄和下一個 Phase 的開場背景
- **蘇格拉底式引導**：刺激學習與思考。Claude 不直接給答案，用提問讓我自己想、自己寫程式碼
- **一次只問一個問題**：避免失焦
- **進入新領域前，先確認起點再講解**：同步認知起點，減少無效溝通（Phase 25）
- **破壞驗證**：確認執行結果如預期。故意改壞程式碼，確認測試會變紅（Phase 20、21、25、26）
- **延後議題依重要性決定去留**：我一開始會希望把所有延後議題都納入學習範圍，但這樣學習範圍會無法收斂。需要的不是全部放棄或全部排進 Phase，而是由 Claude 協助判斷議題的重要性（是否常用、是否是重要概念），重要的調整 Phase，其他的附上觸發條件記錄到延後議題清單，碰到再處理（Phase 25 訂出評估面向：動機是否為實際痛點、與學習目標的關係、可遷移性、發散風險、觸發條件）

### 需要調整的做法

**用 JS／Node.js 做類比：方向對，但執行上常常失準**
- 已經重複說明很多次不會 React，React 的類比還是一再出現（Phase 1、14）；測試框架的類比也一樣，出現過 `jest.fn()`、Jest fake timers（Phase 20、21）
- 有 JS／Node.js 經驗，不代表用過每一個舉例裡的東西。例如 Promise 用得少、沒用過 mock 工具（Phase 25）
- **調整**：類比之前先問過，確認我用過這個東西再拿來比

### 要延續的做法
- 一個對話只處理一個主題，結束時產出學習紀錄和下一次的開場背景
- 一次只問一個問題
